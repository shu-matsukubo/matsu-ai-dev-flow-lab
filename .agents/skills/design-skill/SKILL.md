# 提供能力

入力された能力要求またはSkill定義を読み取りで評価し、他のSkillを知らなくても単独能力として成立する設計案、または設計上のfindingを返す。新規設計、既存定義の変更、分割・統合・削除、設計レビューを、同じ不変条件に対する評価として扱う。

## 適用条件

- 対象能力の目的、利用条件、期待する結果を識別できる。
- 新規設計では候補となる能力境界、既存定義では現在の定義または固定revisionと変更目的を取得できる。
- 適用するrepositoryの安定原則、Workflow責務、共有判断知識または安定したcontractを取得できる。
- 評価対象、対象外、承認scopeを識別できる。

## 入力

- 対象能力の目的、適用場面、期待する入力と出力
- 候補となる能力境界、または現在のSkill定義と変更理由
- repositoryの安定原則、Workflowが所有する工程制御、共有判断知識の正本
- 評価対象、対象外、既に確定した人間判断と承認scope
- 必要に応じて、利用側が期待する能力契約や互換性条件

固定された既存Skill一覧、特定の前後能力、特定Workflowの工程番号は入力の成立条件にしない。

## 出力

- 対象の目的と、単一能力としての境界
- 提供能力、適用条件、入力、出力、責務外、能力固有の処理、失敗時の扱いからなる能力契約案または評価結果
- Skill、Workflow、Reference、`AGENTS.md`、履歴的成果物の配置判定と根拠
- 直接依存、工程依存、状態所有、共有知識の競合する重複に関するfinding
- 分割、統合、維持、削除の判断案、比較案、判断根拠
- 変更が必要な対象と、変更不要な対象
- 未確定な人間判断、未確認事項、remaining risk

出力は設計案または評価結果であり、成果物の変更、承認、実装、他能力の実行、工程遷移、提出完了を意味しない。

## 責務外

- Skill、Workflow、Reference、`AGENTS.md`その他成果物の作成または変更
- Workflowの選択、能力の組み合わせ、実行順序、停止・再開、状態遷移
- 別能力またはAgentの呼び出しと、その成功を成立条件にすること
- Task分解、実装、通常の成果物review、verification、submission
- 要求、設計、承認scope、最終判断を人間に代わって確定すること
- 固定Skill registry、手書きcatalog、既存Skill一覧の所有

## 能力固有の処理

### 設計上の不変条件

1. 対象Skill単体から、提供能力、適用条件、入力、出力、責務外、能力固有の処理、失敗・未実施・不確実時の扱いを判断できる。
2. 対象Skillは別Skillの名前、path、内部仕様、存在、呼び出し、出力取得、成功を、成立条件または処理手順にしない。
3. 必要な前提や利用可能な結果は、特定能力の識別子ではなく、入力となる成果物の性質または能力契約で表す。
4. 対象Skillは特定の前工程・後工程、工程番号、次の能力、Workflowの停止・再開・状態遷移を所有しない。
5. 一つの独立した結果と失敗境界を持つ能力だけを所有し、能力の構成と順序はWorkflowへ残す。
6. 複数能力で共有する判断基準、規約、形式は、競合するコピーを作らずReferenceまたは安定したrepository contractを正本にする。
7. repository全体で長期に安定して守る原則だけを`AGENTS.md`へ置き、具体例、詳細基準、個別能力情報を置かない。
8. 変更対象は明確な違反または能力変更がある範囲へ限定し、履歴的成果物をactive contractとして書き換えない。

### 評価手順

1. 対象の目的と期待する結果を一文で固定する。
2. 7つの能力契約sectionがあり、それぞれに対象固有の意味があるか確認する。
3. 特定能力の識別子、path、存在、呼び出し、出力、成功への依存を確認する。
4. 前後工程、能力の実行順序、停止・再開、状態遷移の所有を確認する。
5. Skill固有処理と、Workflowによる工程制御、共有判断知識、安定原則、履歴的証拠を配置判定する。
6. 共有知識の競合する重複と、追加・名称変更・削除による無関係な変更波及を確認する。
7. 必要に応じて分割、統合、維持、削除を比較し、要求、公開contract、承認scopeを変える判断は未確定事項として返す。
8. findingごとに対象箇所、違反する不変条件、具体的な影響、推奨する配置または表現、未確定事項を示す。

表記の好みだけをfindingにしない。違反がない場合も確認範囲、変更不要の根拠、未確認事項、remaining riskを返す。このSkill自身を評価するときも同じ不変条件を適用する。

### 配置判定

| 記述の性質 | 所有先 | 判定の要点 |
|---|---|---|
| 一つの能力の成立条件、入力、評価または変換、出力、固有の失敗境界 | Skill | 別能力なしでも独立した結果を返せる |
| 能力の選択と組み合わせ、順序、担当構成、承認、停止・再開、状態遷移 | Workflow | 複数能力または工程全体を制御する |
| 複数能力で共有する判断基準、規約、形式、禁止事項、例 | Reference | 処理を実行せず、共有知識を一意に保つ |
| repository全体で長期に安定して守る正本、scope、人間判断、品質、安全、発見原則 | `AGENTS.md` | 詳細手順や個別識別子を持たない |
| 特定時点の設計理由、監査結果、実施証拠 | 設計判断記録またはTask記録 | activeなregistryや将来の更新対象にしない |

### 記述例

`<別能力>`と`<共有基準>`は判断を説明するplaceholderであり、既存能力のcatalogではない。

| 判定 | 記述例 | 理由または置き換え方 |
|---|---|---|
| 禁止 | この処理後に`<別能力>`を呼び出す | 後工程と別能力の存在を前提にするため、能力の構成と順序はWorkflowへ置く |
| 禁止 | `<別能力>`の出力取得または成功を成立条件にする | 必要な成果物の性質と不足時の扱いを入力契約へ記載する |
| 禁止 | Skill自身がWorkflow状態を更新し、次工程を開始する | 停止・再開・状態遷移はWorkflowへ置く |
| 禁止 | 現行Skill名とpathの一覧を本文に保持する | runtime discoveryで能力契約から選択し、固定catalogを作らない |
| 許可 | レビュー結果が入力として与えられている場合は利用する | 特定能力ではなく成果物の性質へ依存している |
| 許可 | `<共有基準>`をReferenceまたは安定したrepository contractから入力する | 変化しやすいSkill間ではなく、一意な共有知識へ依存している |
| 許可 | 別能力の呼び出し、作業順序、状態遷移は責務外と記載する | 依存を要求せず、能力境界を否定文脈で明確にしている |

### 分割・統合・削除

- 独立した出力、適用条件、権限、mutation、失敗境界、再利用理由を持つ責務は分割候補にする。
- 一方の能力がなくても他方が意味のある結果を返せる場合、前後工程として一つのSkillへ統合しない。
- 常に同じ目的、入力、出力、失敗境界を共有し、分割後に単独で意味を持たない記述は統合候補にできる。
- 固有の能力を持たずWorkflow制御だけを包むSkill、安定した別の能力契約で完全に代替されるSkill、利用要求が失われたSkillは削除候補にする。
- 分割、統合、削除によって要求、public contract、承認scope、運用概念が変わる場合は、設計評価だけで確定せず人間判断へ返す。

## 失敗・未実施・残るリスク

目的、現在の定義、安定した責務境界、評価scopeのいずれかを取得できない場合は推測で補完せず、不足する入力、実施できない評価、判断への影響を返す。対象revisionを固定できない場合は確認時点と未確認の変更を明示する。

自然言語の言い換え、削除済みの識別子、暗黙の共有知識は構造検査だけで完全には判定できない。自動検知の成功を完全保証として扱わず、確認範囲、検知できない表現、競合する正本の有無、remaining riskを残す。
