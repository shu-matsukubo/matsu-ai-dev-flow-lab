## 設計結果

要求分析と基本設計では、人間判断が必要な場合だけ進行中のチャットで質問し、回答をその特定事項の確定判断として扱う。回答後は同じ判断への再承認を求めず、工程成果物のPull Request作成まで同じチャットで継続する。

有効なステータスを4種類へ集約し、要求分析、基本設計、最終成果物の完成PRは共通の`人間：PR確認待ち`で表す。タスク計画はGitへ保存しない既存境界を維持するため、`人間：タスク承認待ち`を独立して残す。AI側は`AI：作業可能`の1種類を維持し、工程は永続情報から復元する。

基本設計は設計変更の有無にかかわらず`docs/design-decisions/<issue-id>.md`と設計PRを作成する。現在有効な設計の変更がある場合は同じPRで設計正本も更新し、変更がない場合は影響なしの根拠を記録した設計判断記録だけを変更する。これにより、Issueコメントだけを承認対象にする経路をなくし、完成成果物の確認をPRへ集約する。

## 適用境界

このファイルはIssue #49で承認された目標設計を記録する。設計PRのmergeだけでは、現在有効なAI開発フロー、Agent指示、Skill、契約テスト、GitHubラベルを新契約へ切り替えない。これらは後続の実装Taskで相互に整合した状態へ更新し、外部状態を含む移行条件を確認した時点で有効化する。

実装完了までは`docs/ai-development/overview.md`、`AGENTS.md`、現行Skill、状態契約テスト、および既存repository labelが定める6状態契約を現在有効な規則として扱う。設計PRと現在契約を混同して4状態を先行運用しない。

新契約を有効にするには、少なくとも`人間：PR確認待ち`の実在、後続作業を行うopen Issueの移行、安全停止を含む開始ゲート、文書・Agent・Skill・テスト間の整合を同じ実装境界で確認する。設計判断記録は後続実装の根拠であり、それ単独で作業権やステータスを変更しない。

## 影響評価

| 観点 | 判定 | 根拠 |
|---|---|---|
| frontend / backend責務 | 影響なし | application runtimeの責務やコードを変更しない |
| service境界と依存関係の方向 | 影響なし | Front、API、外部serviceの境界を変更しない |
| API契約 | 影響なし | endpoint、schema、client contractを変更しない |
| authentication / authorization / session | 影響なし | 認証・認可・sessionを導入または変更しない |
| persistence / DBとdata ownership | 影響なし | applicationの永続化を変更しない。GitHubラベルとGit内の設計判断記録だけを扱う |
| セキュリティ境界 | 既存設計の明確化 | `AI：作業可能`の自己付与禁止、競合・未付与・旧ラベル残存時の安全停止を維持する |
| テスト戦略とCI / 品質ゲート | 既存設計の明確化 | 共通品質ゲートは維持し、4状態、旧ラベル、質問有無の4経路、設計PRの契約確認を追加対象にする |
| AI開発フロー | 設計判断が必要 | 6状態から4状態への集約、基本設計成果物の常時PR化、回答済み判断の再承認禁止を定義する |
| Agent / Skill責務 | 設計判断が必要 | Mainの開始・引き渡し責務、要求分析と基本設計の同一チャット継続、後続Skillの状態契約を整合させる必要がある |

## ステータス契約

| 有効なステータス | 意味 |
|---|---|
| `人間：要求承認待ち` | 新規Requirement Issueの要求確認 |
| `AI：作業可能` | 現在のチャット指示を受けたAIの作業権 |
| `人間：PR確認待ち` | Requirement Analysis PR、設計PR、またはIssue統合PRの確認 |
| `人間：タスク承認待ち` | チャット上のタスク計画の確認 |

`人間：要求分析承認待ち`、`人間：基本設計承認待ち`、`人間：最終成果物承認待ち`は廃止対象とする。移行中も通常ラベルとして無視せず、付与されている場合は永続情報を確認して有効な状態へ移行するまで開始ゲートで停止する。新契約の有効化前に`人間：PR確認待ち`を用意し、後続作業を行うopen Issueを個別に移行する。AIは移行によって自ら`AI：作業可能`を取得しない。

## 工程と承認境界

```text
要求分析開始
  -> 必要な場合だけ同じチャットで質問・回答
  -> 要求分析書 + Requirement Analysis PR
  -> 人間：PR確認待ち

Requirement Analysis PR merge後の基本設計
  -> 必要な場合だけ同じチャットで質問・回答
  -> 設計判断記録 + 必要な設計正本変更 + 設計PR
  -> 人間：PR確認待ち

設計PR merge後
  -> 最新正本を確認
  -> 新しい設計判断がなければタスク計画
  -> 人間：タスク承認待ち

タスク計画承認後
  -> 既存の実装・レビュー・検証・二階層PR
  -> Issue統合PRを確認可能にする
  -> 人間：PR確認待ち
```

質問中は`AI：作業可能`を維持する。人間の回答は質問で特定した判断について確定済みとし、回答後に途中成果物の承認状態へ切り替えたり、同じ判断を再質問したりしない。正式な状態遷移は完成PRまたはタスク計画を引き渡すときだけ行う。

## 設計判断記録の責務

- Requirement Issueごとに1ファイルを使用し、同じIssueで要求分析改訂または追加設計が生じた場合は最新の判断へ更新する。
- 元Issue、merge済み要求分析書、9観点の影響分類と根拠、確定した判断、現在有効な設計正本への反映有無、未確定事項、未対象、残るリスクを記録する。
- 現在有効な設計正本を置き換えず、設計変更がある場合は同じ設計PRで該当する正本も更新する。
- 要求・設計の全文、具体的なTask、実装対象ファイル、作業順序、Agent割り当てを複製しない。
- 設計変更がない場合も記録だけを変更する設計PRを作り、PRのmergeを基本設計完了の永続的な根拠にする。

## 重要な人間判断

| 判断対象 | 採用した判断 | 比較した案 | 根拠 |
|---|---|---|---|
| ステータス数 | 4状態へ集約する | 現行6状態を維持する、すべての人間待ちをまとめた3状態にする | 現行6状態より操作と契約を単純化しつつ、PR確認とGitに保存しないタスク計画をGitHub UI上で区別できる |
| PR確認状態 | 要求分析、基本設計、最終成果物を`人間：PR確認待ち`へ統一する | 工程別のPR確認ラベルを維持する | 確認対象の具体的なPRと工程は永続情報から復元でき、工程別ラベルを重複して持つ必要がない |
| AI作業可能状態 | `AI：作業可能`の1種類を維持する | 工程別AIラベルへ分割する | 人間の操作を増やさず、次工程はmerge済み成果物とPRから一意に復元できる |
| 設計変更なしの成果物 | 設計判断記録を追加する設計PRを作る | Issueコメントだけで承認する、差分のないPRを使う | 基本設計の完成成果物をレビュー可能なGit差分とPRに統一し、後続工程の復元根拠を残せる |

これらの判断は、2026-09-05の基本設計チャットで要求者が推奨案を承認したことに基づく。

## 品質と安全性

- `AI：作業可能`と現在のチャット指示の両方を開始条件とし、ラベルだけで自動起動しない。
- 有効ステータス未付与、複数競合、旧ラベル残存、永続情報との不整合では安全側に停止する。
- 人間の回答、Pull Requestの内容とmerge、タスク計画の承認をラベルで置き換えない。
- AI agentはPull Requestをmergeせず、Requirement Issueをcloseしない。
- 共通品質ゲート`sh scripts/verify.sh`を維持し、状態契約と4経路を変更リスクに応じた追加検証で確認する。

## 未対象・未充足

- 現在有効なAI開発フロー、Agent指示、Skill、状態契約テスト、Requirement Issue Formその他の実行規則への反映は後続Taskで扱う。
- `人間：PR確認待ち`のrepository label作成、open Issueの状態移行、廃止対象ラベルの整理は後続Taskまたは人間が管理する外部状態の確認で扱う。
- タスク計画、実装対象、作業順序、Agent構成はこの設計PRでは決定しない。

## 残るリスク

- GitHub上の新ラベルが用意される前に新契約を有効にすると引き渡し不能になるため、新ラベルの実在と移行状態を外部確認する必要がある。
- ステータス名を共通化しても、PRやmerge済み成果物を読まずに工程を判断すると誤復元するため、永続情報との照合を必須とする。
