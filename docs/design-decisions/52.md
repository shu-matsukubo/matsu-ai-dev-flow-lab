## 設計結果

AI開発フローを、安定原則、Workflow、単一能力、共有判断知識の4層へ分離する。依存方向はWorkflowから必要な能力契約とReferenceへ向かう一方向とし、`AGENTS.md`と個別SkillにはWorkflowの順序や別Skillの識別名を持たせない。

`docs/ai-development/overview.md`はAI開発フローの入口と正本の案内を担い、工程の制御は`docs/ai-development/workflows/`、複数能力で共有する判断知識は`docs/ai-development/references/`へ分離する。個別Skillは実行時に発見できる単一能力として`.agents/skills/`に置き、固定Skill一覧を重複管理するregistryは作らない。

Workflowは「要求を分析する」「設計影響を評価する」「レビューする」「検証する」「提出する」のように必要な能力と期待する出力を記述する。特定のSkill名を呼び出さず、実行時点で提供されるSkill一覧の`name`、`description`と本文の能力契約、およびReference directoryを確認して利用可能な能力を選択する。

## 適用境界

このファイルはIssue #52で承認された目標設計を記録する。設計PRのmergeだけでは、現在有効な`AGENTS.md`、AI開発フロー、Skill、Agent定義、契約テストを新構造へ切り替えない。

実装完了までは現在の`docs/ai-development/overview.md`、`AGENTS.md`、9つの既存Skill、`.codex/agents/`、`tests/requirement-status-contract.test.mjs`を有効な規則として扱う。目標設計の一部だけを先行適用し、開始ゲート、承認境界、提出規則が複数箇所で食い違う状態を作らない。

新構造は、Workflow、Agent指示、能力Skill、Reference、契約テストの整合と既存の品質・安全境界を同じ移行境界で確認できた時点で有効化する。設計判断記録は後続実装の根拠であり、それ単独で作業権、Issueの状態、Pull Requestの状態を変更しない。

## 現在の依存関係の棚卸し

### AGENTS.md

現在の`AGENTS.md`は9つの個別Skillを識別名で列挙し、要求分析、設計影響確認、タスク計画、実装、レビュー、検証、提出、Flow Feedback処理の順序と遷移を直接制御している。また、開始ゲート、二階層PR、Task記録、検証、提出、安全規則の詳細も保持している。

このうち、正本の分離、現在の証拠を直接確認すること、承認scopeを広げないこと、未確定な人間判断を推測で確定しないこと、適切なレビュー・検証・提出、remote操作とsecret、AIによるmerge・branch削除・Issue close禁止は安定原則として残す。工程順序、個別成果物、状態遷移、Task・PR手順、個別Skill名はWorkflowまたはReferenceへ移す。

### 重複している判断知識

現在は次の判断が`AGENTS.md`、`overview.md`、複数Skill、契約テストへ重複している。

- 4種類のステータス、開始ゲート、停止・再開、Mainだけが行う引き渡し
- Requirement Analysis PR、設計PR、Task PR、Issue統合PRの境界
- `Refs #<number>`と自動close keyword禁止
- GitHub連携だけを使うremote操作、AIによるmerge・branch削除・Issue close禁止
- Task分解とAgent構成の選択基準
- review観点とfindingの重要度
- 共通品質ゲート、追加検証、未実施と残るリスク
- Flow Feedbackの記録形式、3分類、3 directory状態、Main単一writer

工程を動かす規則はWorkflow、複数能力で使う判断基準はReference、repository全体で常に守る安全原則は`AGENTS.md`へ一つずつ配置し、同じ判断の競合する複製を残さない。

## 目標アーキテクチャ

| 層 | 所有する責務 | 所有しない責務 |
|---|---|---|
| `AGENTS.md` | 正本、現行証拠、承認scope、人間判断、品質、安全、能力発見の安定原則 | 個別Skill名、工程順序、成果物別手順、Skill固有規則 |
| Workflow | 作業分解、必要能力、実行順序、Agent構成、承認、停止・再開、状態遷移、成果物とPRの統合境界 | 個別能力の処理手順、特定Skillの存在、共有判断基準の詳細 |
| Skill | 一つの能力の適用条件、入力、処理、出力、失敗・未実施・残るリスク | 別Skill、前後工程、承認状態、Workflow遷移、能力外のTask管理や提出 |
| Reference | 複数能力で共有する判断基準、形式、禁止事項、例 | 処理実行、Agent割り当て、状態遷移、別能力の呼び出し |
| Agent定義 | Main、Worker、Reviewerの役割とmodel / reasoning effort | Workflow固有のSkill一覧や工程順序 |
| 契約テスト | 層の依存方向、能力契約、既存の品質・安全境界 | 固定Skill一覧やSkill本文へのWorkflow複製の強制 |

依存方向は次のとおりとする。

~~~text
人間の現在の指示 + 永続状態
  -> Workflowが現在工程と必要能力を決定
      -> 実行時に利用可能なSkillを能力契約で選択
      -> 必要なReferenceを判断知識として参照
      -> Skillが結果・失敗・未実施・残るリスクを返す
  -> Workflowが結果を確認して停止・継続・承認引き渡しを決定
~~~

SkillとReferenceからWorkflowへ遷移を要求せず、Skill同士も依存しない。

## AGENTS.mdの安定責務

`AGENTS.md`には次を残す。

- Requirement Issue、要求分析、設計、実装、作業記録の正本を分離する
- 過去チャットやラベルだけでなく、現在有効な要求・設計・実装・永続状態を直接確認する
- 現在の人間指示と承認scopeを超えて変更しない
- 要求または設計上の未確定な人間判断をAIだけで確定しない
- 作業リスクに適したreview、verification、submissionを行い、未実施項目と残るリスクを示す
- 必要な手順では、実行時点で利用可能なWorkflow、Skill、Referenceを確認し、能力契約から選択する
- secret、credential、個人情報、危険なremote操作を避ける
- AI agentはPull Requestをmergeせず、branchを削除せず、Requirement Issueをcloseしない

具体的なSkill識別名、Skillを呼ぶ順序、4状態の遷移表、成果物別PR本文、Task file手順、Flow Feedbackの処理手順は置かない。

## Workflowの責務

Workflowは`docs/ai-development/workflows/`を正本とし、`overview.md`はWorkflow群への入口と、正本間の関係を示す。Workflowは次を所有する。

- 現在のRequirement Issueの作業開始ゲートと永続情報からの工程復元
- 要求分析、設計影響確認、タスク計画、実装、Issue統合の成果物と承認境界
- 作業に必要な能力、入力、期待する出力と実行順序
- 標準、高リスク、小規模の成果物作成パターンとAgent構成
- Task記録、Issue branch、Task branch、二階層PR、最新`develop`同期
- Flow Feedbackの評価案承認、処理反映、引き継ぎ先の最終結果までの状態
- 完成成果物だけを人間承認待ちへ引き渡す規則と、同じ指示では次工程へ進まない停止

Workflowは特定Skill名を列挙せず、必要な能力を意味と入出力で記述する。能力が追加・名称変更・削除されてもWorkflowの要求能力が変わらない限り、Workflow文書を変更しない。

## Skillの能力契約

各Skillはfront matterの`name`と`description`を自己宣言とし、本文で少なくとも次を識別できる共通構造を持つ。

- 提供能力
- 適用条件
- 入力
- 出力
- 責務外
- 能力固有の処理
- 失敗、未実施、残るリスクの返し方

別Skillの識別名、特定の前工程・後工程、Issueのステータス遷移、次工程の開始、能力外のTask記録やPR公開を記載しない。提出能力だけがremote変更を実行できるが、成果物種別、base、head、公開形式、本文、禁止事項はWorkflowとReferenceが確定した入力として渡し、提出能力自身は工程を選択しない。

レビュー能力は対象、要求・設計、review criteria、既知の検証結果を入力とし、重要度付きfinding、確認範囲、未確認事項、remaining riskを返す。他能力を呼び出さず、Task記録や状態を更新しない。

検証能力は対象、要求・設計、verification criteria、利用可能な環境を入力とし、各確認をPassed / Failed / Not Executedで分類し、根拠とRemaining Riskを返す。結果を受けた修正、再実行、提出、遷移はWorkflowが判断する。

## 能力の構成

既存Skill名の温存は設計目標にしない。目標構造では少なくとも次の独立能力を利用できるようにする。

- 要求を分析し、要求分析成果物または未確定判断を返す能力
- 現在の設計と実装への影響を評価し、設計判断成果物または未確定判断を返す能力
- 要求と設計から単一責務のTask案を作る能力
- 成果物またはdiffをレビューし、findingとremaining riskを返す能力
- 成果物またはdiffを検証し、Passed / Failed / Not Executed / Remaining Riskを返す能力
- 確定済みの提出契約に従い成果物を公開し、提出結果と未完了境界を返す能力
- 観測事実から新しいFlow Feedbackを1件記録する能力
- 固定済みのFlow Feedback集合を読み取り評価し、分類案とremaining riskを返す能力
- 人間承認済みのFlow Feedback処理を記録とfile配置へ反映し、反映結果を返す能力

AgentやWorkflowを統括すること自体は単一能力Skillにせず、WorkflowとMainの責務とする。

## Referenceの責務と形式

共有Referenceは`docs/ai-development/references/`へ置き、少なくとも次の判断知識を一意な正本として分離する。

- review criteriaとfindingの重要度
- verification criteria、共通品質ゲート、追加検証、未実施の扱い
- Task分解とAgent構成の判断基準
- submission、branch、Pull Request本文、非自動close参照、未完了境界
- security、secret、credential、remote操作、破壊的操作
- Flow Feedbackの記録形式、評価分類、directory状態

各Referenceは目的、適用対象、判断基準、対象外、根拠となる設計への参照を示す。処理を命令する手順、工程の開始・終了、状態遷移、別能力の呼び出しを持たない。

正本を分けすぎて同じ判断を複数Referenceへ複製しない。`overview.md`は個別基準の本文を複製せず、WorkflowとReference directoryへの入口を提供する。

## 能力とReferenceの発見

固定registryや、全Skill名を列挙する手書きcatalogは作らない。

エージェントは実行時に提供される利用可能Skill一覧から`name`と`description`を確認し、必要な能力に合う候補の`SKILL.md`を読んで入出力と責務外を照合する。Referenceは`docs/ai-development/references/`を列挙し、各文書の目的と適用対象から選択する。

Workflowは必要な能力と期待する出力だけを指定する。該当能力が存在しない、複数候補を安全に選べない、入力契約を満たせない場合は、無関係なSkillや`AGENTS.md`を変更して補完せず、不足または未実施としてWorkflowへ返す。Workflowは承認scopeと安全境界の範囲で代替を選ぶか、変更前に停止する。

この方式ではSkillの追加・名称変更・削除によって変更されるのは当該Skillと、その能力自体が変わる場合のWorkflowまたはReferenceだけであり、無関係なSkillと`AGENTS.md`には変更を要求しない。

## 成果物作成パターン

Workflowは特定Skill名ではなく、次の役割と能力で構成を選ぶ。

| パターン | 構成 |
|---|---|
| 標準 | 必要に応じたTask分解、Workerによる作成とself review、Mainによる成果物・レビュー・検証結果の確認、提出 |
| 高リスク | Task分解、Workerによる作成とself review、独立Reviewerによるreview、Mainによる最終確認とverification、提出 |
| 小規模 | Mainによる作成、self review、verification、提出 |

独立Reviewerの追加は、security、不可逆変更、public contract、複数境界、部分失敗、統合複雑性など、独立した観点で検出したい具体的リスクがある場合に選ぶ。ファイル数や変更行数だけで決めない。どのパターンでもMainが実成果物、review結果、verification結果、未実施項目、残るリスクを確認して最終判断する。

## Agent責務

MainはWorkflowの選択、開始ゲート、永続状態からの復元、必要能力とReferenceの発見、Agent構成、承認境界、停止・再開、統合、最終判断を所有する。個別能力の出力だけで工程完了を推測せず、現在の成果物と永続情報を直接確認する。

Workerは割り当てられた能力とscopeの範囲で成果物を作成し、必要なself reviewとverificationを行い、結果、未実施、残るリスクをMainへ返す。Reviewerは実装担当から独立し、指定されたreview能力の入力と基準に従いfindingとremaining riskをMainへ返す。

WorkerとReviewerはWorkflowの状態を変更せず、承認scope、能力の選択、次工程、提出を独断で変更しない。modelとreasoning effortは引き続き`.codex/`が所有し、SkillまたはWorkflowへ複製しない。

## 品質と安全性

次の既存境界を維持する。

- Requirement Issue作業は最新Issueの有効な作業可能状態と現在の人間指示の両方を開始条件とする
- 人間承認待ち、未付与、競合、旧状態、永続情報との不整合では変更前に停止する
- 正本と人間承認をラベルや過去チャットで置き換えない
- 承認されたscopeを拡張せず、新しい要求または設計判断をAIだけで確定しない
- 共通品質ゲート`sh scripts/verify.sh`と変更リスクに応じた追加検証を維持する
- remote操作はGitHub連携だけを使用し、`git push`、`gh`、GitHub APIへの直接`curl`へ切り替えない
- secret、credential、個人情報、実案件固有情報を成果物へ記録しない
- Pull Requestのmerge、branch削除、Requirement Issueのcloseは人間だけが行う
- PRはRequirement Issueを非自動close形式で参照し、Issue統合時に全受入条件の根拠、未実施、残るリスクを示す

安定原則は`AGENTS.md`、工程制御はWorkflow、詳細判断はReference、実行結果はSkillへ配置し、同じ文言を全層へ複製することを安全性の条件にしない。

## 検証設計

共通品質ゲートとCIの入口は変更しない。AI開発フローの契約テストは、現在の固定Skill一覧と全Skillへの状態契約複製を要求する方式から、次の動的検証へ変更する。

- `.agents/skills/*/SKILL.md`を固定名なしで列挙し、front matterと能力契約の必須項目を確認する
- `AGENTS.md`に個別Skill識別名、特定Skillの存在、Skill固有の実行順序がないことを確認する
- 各Skillの自己宣言を除き、別Skillの識別名や呼び出しがないことを確認する
- 能力SkillにWorkflowの状態遷移、前後工程、能力外のTask管理・提出制御がないことを確認する
- Workflowが必要能力を意味と入出力で示し、個別Skill名を列挙しないことを確認する
- Referenceが判断知識だけを持ち、処理実行、Agent割り当て、状態遷移を持たないことを確認する
- 開始ゲート、4状態、承認、停止・再開、二階層PR、人間だけのmerge・closeをWorkflowと安全原則から確認する
- 標準、高リスク、小規模の3パターンとreview、verification、submissionの完了境界を確認する
- fixture上で代表能力の追加、名称変更、削除を模擬し、`AGENTS.md`と無関係なSkillの変更を必要としないことを確認する
- applicationのlint、typecheck、Unit Test、buildと`git diff --check`を引き続き実行する

文字列の単純一致だけで正当な自己宣言やReference参照を誤検出しないよう、対象directoryと文書区分を識別して検証する。固定Skill数や名称を新しい契約として再導入しない。

## 重要な人間判断

| 文書構造 | `overview.md`を入口にし、WorkflowとReferenceを`docs/ai-development/`配下へ分離する | `overview.md`一冊へ維持する | Workflow変更と共有基準変更を局所化し、肥大化した単一文書の再結合を避ける |
| 発見方式 | 実行時のSkill一覧とReference directoryを能力契約で探索し、固定registryを作らない | machine-readable registryでSkillを対応付ける | Skill metadataの二重管理と、名称変更時に必ず更新する中央依存点を作らない |
| Workflow表現 | 必要能力を意味・入力・期待出力で記述し、個別Skill名を列挙しない | Workflowが具体的なSkill名を呼び出す | 能力の置換と名称変更をWorkflow制御から分離する |
| Skill構造 | 全Skillへ共通の能力契約を持たせ、別Skill、前後工程、状態遷移を除く | 現行Skillを残して相互参照だけを弱める | 単一能力として独立利用できることを構造とテストで確認可能にする |
| orchestration | `coordinate-approved-tasks`相当の統括責務をWorkflowとMainへ移す | 統括Skillを残す | 複数能力の順序、承認、Task・PR遷移は能力ではなくWorkflowの責務である |
| Flow Feedback | 読み取り評価と人間承認済み反映を分離する | 評価、承認待ち、更新、Issue引き継ぎを一つのSkillに残す | 評価結果と外部変更を分け、承認前のmutationを能力内部へ混在させない |

## 残るリスク

- 実行環境が提示するSkill一覧の形式が変わる場合でも、特定のcatalog実装へ依存せず能力説明を確認できる必要がある。
- WorkflowとReferenceの分割粒度が細かすぎると探索コストが増えるため、同じ判断を複製しない範囲で関連事項をまとめる必要がある。
- 単純な禁止語検査だけでは正当な自己宣言や歴史的な設計記録を誤検出しうるため、activeなWorkflow、Skill、Referenceを区別した検証が必要である。
- 既存の状態契約テストは現在の重複構造を意図的に強制しているため、新構造への移行時は安全境界を失わずに検証対象を切り替える必要がある。
