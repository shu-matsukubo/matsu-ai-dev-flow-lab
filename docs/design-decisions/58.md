## 設計結果

高難度、高リスク、または不確実性の高い判断について、作業中の元Agentが現在の承認scope内で専門レビューを依頼し、助言を評価して元の作業へ戻る独立能力を追加する。

独立能力の識別名は request-expert-review、専門レビュー担当の役割識別名は expert-reviewer とする。前者は実行時の能力一覧から発見できる単一能力、後者はCodexのproject-scoped custom Agentとして扱う。

専門レビューは担当変更やWorkflow上のAgent構成変更ではなく、元Agentが自身の判断を補強するための限定的な相談である。Main、Worker、Reviewerのいずれも、自身に与えられたscopeと権限の範囲で必要性を判断し、人間の都度承認なしで依頼できる。専門レビュー担当は成果物の作成主体、Workflow制御、要求・設計の確定、承認、提出、最終判断を引き継がない。

SkillとWorkflowは具体的なmodel名、reasoning effortの機械値、provider固有識別子を持たない。expert-reviewerと実際のmodel、reasoning effort、sandboxの対応はAgent設定だけが所有する。現時点では利用可能な最上位modelと、そのmodelが対応する最大のreasoning effortを割り当てる。

依頼には必要最小限の明示的な情報だけを渡し、会話履歴全体を不要に継承しない。専門レビュー担当はread-onlyとし、外部状態の変更、追加権限の取得、再エスカレーション、子Agentの起動を行わない。

## 適用境界

この文書はIssue #58の目標設計を記録する。設計PRのmergeだけでは、専門レビュー能力、expert-reviewer、Workflow統合、追跡記録、契約テストを有効化しない。

現在有効なAGENTS.md、Workflow、Skill、Reference、Agent定義、契約テストは、後続実装で相互に整合した変更と検証が完了するまで維持する。設計の一部だけを先行適用し、通常Agentが存在しない役割を呼び出したり、利用不能を成功扱いしたりしない。

この設計はTask分解、実装対象fileの確定、作業順序、Agent割り当てを行わない。設計PRの人間merge後、別チャットで最新の正本を読み直し、追加設計が不要な場合にだけTask計画へ進む。

## エスカレーション判断

元Agentは、作業内容、失敗時の影響、可逆性、復旧コスト、不確実性、自身の判断困難度を総合し、専門レビューの必要性を文脈から判断する。

次は代表的な判断材料であり、固定チェックリストや自動採点にはしない。

- security、authentication、authorization、permission、secretに関わる判断
- data loss、migration、不可逆操作、復旧コストが高い変更
- 大規模または不可逆性の高いarchitecture判断
- public contract、複数service、部分失敗、統合複雑性を伴う変更
- リリース前など、失敗時の影響が大きい重要な確認
- 元Agentが前提、根拠、結論に高い不確実性または判断困難を認識した場合

低影響で可逆的であり、要求、設計、既存の確認結果から判断が十分に明確な場合は、専門レビューを依頼しない判断を選べる。利用しなかったことを全作業で定型記録しない。

専門レビューが必要と判断された場合、依頼自体への人間の事前承認は追加しない。ただし、依頼元が持たないscope、権限、要求判断、設計判断、人間承認を専門レビュー経由で取得したことにはしない。

## 責務と依存方向

~~~text
現在の指示と永続状態
  -> Workflowが工程、承認scope、必要な成果物を決定
      -> 元Agentが作業と判断を行う
          -> 高難度・高リスク・高不確実性を文脈から認識
          -> runtimeの能力契約から専門レビュー能力を選択
              -> request-expert-reviewがexpert-reviewerへ必要最小限の依頼を渡す
              -> expert-reviewerがreviewと助言を返す
          -> 元Agentが正本と承認scopeへ照合し、対応を決定
      -> 元Agentが通常のWorkflowへ結果を戻す
~~~

Workflowは個別Skill名、具体的なrole識別名、model設定を所有せず、必要な能力、適用条件、入力、期待する出力、責務の戻り先を意味で表す。

request-expert-reviewは呼び出し元の個別Skill名、工程名、前後工程、成果物種別、Workflow状態を知らない。expert-reviewerという役割へ依頼することと、依頼および結果の契約だけを所有する。

expert-reviewerは指定された論点と資料を独立した観点で確認し、reviewと助言だけを返す。元Agentは回答を無条件に採用せず、現在の要求、設計、成果物、既知のreview、verification、承認scopeと照合する。

Mainは引き続きWorkflow選択、正式なAgent構成、承認、停止・再開、成果物統合、最終判断を所有する。WorkerまたはReviewerによる専門レビュー依頼は、書き手や承認者を追加せず、scopeと完了条件を変更しない限定的な相談であるため、Task再計画または都度の人間承認を必要とするAgent構成変更には数えない。

## 依頼契約

元Agentは少なくとも次を明示して依頼する。

- 確認したい論点
- 専門レビューが必要と判断した理由
- 対象範囲と対象外
- 関連する要求、受入条件、設計、成果物または固定revision
- 確認済みの事実と未確認の仮定
- 承認scope、権限、安全、時間などの制約
- 期待する確認結果

依頼は必要な情報を明示的に構成し、会話全文、secret、credential、個人情報、実案件固有情報を不要に渡さない。入力が不足し、追加情報なしでは有効な確認ができない場合、専門レビュー担当は推測で補わずInsufficient Inputを返す。

## 結果契約

専門レビュー結果は次の状態を区別する。

| 状態 | 意味 |
|---|---|
| Completed | 指定された範囲を確認し、利用可能な結果を返した |
| Unavailable | role、能力、tool、実行枠、環境などが利用できない |
| Insufficient Input | 必要な要求、設計、対象、制約または証拠が不足している |
| No Result | 実行を開始したが、利用可能な回答を取得できなかった |

Completedでは少なくとも次を返す。

- 重要度を識別できるfinding
- findingごとの助言と判断根拠
- 使用した前提
- 確認範囲
- 未確認事項
- 追加の人間判断が必要な事項
- remaining risk

findingの重要度は既存のレビュー基準と整合させる。指摘がない場合も、確認範囲、未確認事項、remaining riskを示す。

Completed以外では状態、理由、未確認事項、代替確認の可否、remaining riskを返す。これらを通常reviewまたはverificationの成功として扱わない。

元Agentは各findingについて対応、非対応、追加確認、または人間判断への引き渡しを決め、理由を現在の正本と承認scopeへ対応付ける。専門レビューの回答だけで要求、設計、承認scope、提出可否を確定しない。

## 専門レビュー担当

専門レビュー担当の役割識別名はexpert-reviewerとする。責務は、高難度、高リスク、または高不確実性の論点を独立してreviewし、助言と残るリスクを返すことである。

Agent設定は次の境界を持つ。

- nameとdescriptionで役割と利用場面を明示する
- 利用可能な最上位modelと、そのmodelが対応する最大のreasoning effortを設定する
- sandboxをread-onlyにする
- 成果物、記録、外部状態を変更しない
- 要求、設計、承認、提出、最終判断を引き継がない
- 子Agentを起動せず、多階層エスカレーションを行わない
- 不足情報を推測で補わず、未確認事項とremaining riskを返す

具体的なmodelとreasoning effortの機械値はAgent定義だけに置く。呼び出し元、Workflow、Skill、Reference、AGENTS.mdへ複製しない。roleを起動するときもmodelまたはreasoning effortを個別overrideせず、Agent定義を利用する。

Codexのproject-scoped custom Agentは.codex/agents配下の独立した設定でname、description、developer instructions、model、reasoning effort、sandboxを所有できるため、この責務分離を構成上確認できる。

## 追跡可能性

request-expert-reviewは、呼び出し元が保存できる次の要約を結果へ含める。

- 利用理由
- 確認対象
- 専門レビューの状態と主要な結果
- 元Agentの対応判断と根拠

保存先はWorkflowが所有する既存の永続成果物とし、専門レビュー専用の中央directoryや台帳を追加しない。

- 要求分析では要求分析成果物またはRequirement Analysis PR
- 設計では設計判断記録または設計PR
- Task実装、review、verificationではTask記録またはTask PR
- Issue統合、リリース前確認ではIssue統合PRまたは対応する既存成果物
- Git成果物またはPRが作られずWorkflowが終了する場合はRequirement Issue上の追跡可能な記録

同じ内容を複数箇所へ全文複製しない。正式な引き渡し前に、利用理由、対象、主要結果、元Agentの判断をいずれか一つの永続成果物から確認できる状態にする。チャット全文や専門レビュー回答全文の保存を要求しない。

Skillは保存先や成果物形式を選ばず、入力で指定された追跡先に利用できる要約だけを返す。永続化、PR更新、Issue操作、工程遷移は元AgentとWorkflowの責務とする。

## 既存フローとの統合

専門レビュー能力は要求分析、設計影響確認、Task計画、成果物作成、review、verification、Issue統合、リリース前確認のいずれからも同じ契約で利用できる。

AGENTS.mdには個別Skill名やrole名を追加せず、高難度、高リスク、高不確実性時に利用可能な専門レビュー能力を承認scope内で選択し、結果と残るリスクを照合する安定原則だけを置く。

Workflowには、全工程で利用できる任意の専門レビュー、元Agentへの責務の戻り先、正式な引き渡し前の追跡を意味で記載する。個別Skill名、role名、model設定は記載しない。

通常の独立Reviewerは、承認済みAgent構成に基づいて成果物全体を必須経路としてreviewする。専門レビューは、元Agentが特定論点の難度、リスク、不確実性から必要時に追加する相談である。専門レビューを実行しても、通常のself review、独立review、Main review、verification、提出を置き換えない。

他の能力Skillは専門レビュー能力の識別名を知らず、専門レビューの追加または名称変更を理由に変更しない。runtimeに提示される能力のdescriptionと契約から必要時に選択する。

## 検証設計

共通品質ゲートとCIの入口は変更しない。後続実装では、既存の動的な能力契約テストへ次を追加する。

- 専門レビュー能力がruntimeのname、description、能力契約から一意に発見できる
- 専門レビュー能力が呼び出し元の個別Skill名、工程名、Workflow状態、成果物種別に依存しない
- 他の能力Skillが専門レビュー能力の識別名に依存しない
- AGENTS.mdとWorkflowが個別Skill名、role名、具体的なmodel名、reasoning effortの機械値を持たない
- expert-reviewerのAgent定義だけが具体的なmodel、reasoning effort、read-only sandboxを所有する
- role起動時にmodelとreasoning effortをoverrideせず、Agent設定だけで差し替えられる
- 専門レビュー担当が成果物変更、Workflow制御、承認、提出、外部変更、子Agent起動を責務に持たない
- 依頼と結果が必要項目、失敗状態、追跡要約を持つ
- 専門レビューの追加または名称変更で、AGENTS.mdと無関係なSkillの変更を必要としない

変更リスク固有の確認では、次の代表事例を同じ能力契約で再現する。

| 事例 | 期待する確認 |
|---|---|
| securityまたは復旧困難な高リスク判断 | 専門レビューを依頼し、元Agentが結果を評価して作業へ戻す |
| 元Agentが自身の判断困難または高い不確実性を認識 | 固定チェックリスト外でも依頼できる |
| 低影響で可逆的かつ判断根拠が明確 | 専門レビュー不要と判断でき、定型記録を要求しない |
| roleまたは能力が利用不能 | Unavailableとして理由、未確認事項、remaining riskを返し、成功扱いしない |
| 入力不足 | Insufficient Inputとして不足項目を返し、推測で結果を作らない |
| 実行後に有効な結果を取得できない | No Resultとして通常review成功と区別する |

共通入口sh scripts/verify.sh、文書構造、依存方向、secretと外部変更の否定経路を確認し、Passed、Failed、Not Executed、Remaining Riskを分けて記録する。

## 重要な人間判断

| 判断対象 | 採用した判断 | 比較した案 | 根拠 |
|---|---|---|---|

| 入力範囲 | 必要最小限の明示的な依頼を渡し、会話全文を不要に継承しない | 親Agentの全履歴を常に渡す | secretや無関係な実案件情報の拡散を避け、依頼契約を再現可能にする |
| model設定 | roleと具体設定の対応をAgent定義だけが所有する | SkillまたはWorkflowがmodelと推論レベルを指定する | Issue #52の依存方向を維持し、設定変更を局所化する |
| 専門レビュー担当の権限 | read-onlyで助言に限定し、子Agentを起動しない | 元Agentと同じ変更責務を持つ、多段エスカレーションを許可する | 作業主体と既存承認境界を維持し、権限拡大と再帰を防ぐ |

具体的なTask境界、実装対象file、作業順序、Agent構成は、設計PRの人間merge後に別チャットで現在の正本を読み直して扱う。

## 残るリスク

- runtimeのsubagent機能またはcustom Agentの利用可否は実行環境に依存する。利用不能を正常な専門レビュー完了と区別する必要がある。
- 文脈判断は固定ルールではないため、同じ事例でもAgentによって依頼要否が揺れる可能性がある。代表事例と判断根拠の確認で意図した裁量範囲を検証する必要がある。
- WorkerまたはReviewerの直接依頼を担当変更と誤認すると、不要な再承認または無断のscope拡大につながる。限定的な相談である境界をWorkflow、Agent指示、契約テストで一致させる必要がある。
- 必要最小限の入力でも、依頼構成時にsecretや実案件固有情報を含める可能性がある。入力時の除外と永続記録の要約範囲を確認する必要がある。
- modelの利用可能性や最大reasoning effortは将来変わりうる。Agent設定だけを更新し、SkillとWorkflowへ設定依存を波及させない必要がある。
- 専門レビューの成功だけでは通常review、verification、提出の完了を保証しない。既存品質ゲートを代替しないことを統合確認する必要がある。
