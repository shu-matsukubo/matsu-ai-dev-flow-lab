## 設計結果

Requirement Issueの長時間維持するステータスを、`AI：作業可能`と`人間：PR確認待ち`の2種類へ限定する。ステータスは工程名や成果物の承認状態ではなく、AIが現在のチャット指示に従って作業できるか、完成Pull Requestを人間が確認する番かだけを示す。

工程は、Issue、merge済みPull Request、要求分析書、設計判断記録、Task記録、実装、review、verification、CIから復元する。状態遷移、開始・停止、正式な引き渡し、工程復元はRequirement Issue lifecycleのWorkflowだけが所有し、`AGENTS.md`、個別Skill、Reference、Agent定義へ状態機械を複製しない。

新規Requirement Issueには初期ステータスを付与しない。AIが要求原文をIssueとして登録した段階では、人間による内容確認が済んでいないためである。人間がIssueを確認して`AI：作業可能`を付与し、現在のチャットで対象Issueと作業を指示した場合だけ開始できる。未付与は第3の有効状態ではなく、開始前の安全停止条件である。

要求分析、設計影響確認、Task Planning、実装中に必要となる人間判断は進行中の同じチャットで完結させる。質問中も長時間状態は`AI：作業可能`のままとし、回答後は同一事項への別承認、ラベル変更、新しいチャット指示なしで、その工程の正式な引き渡し点まで継続する。

## 適用境界

このファイルはIssue #67で承認された目標設計を記録する。設計PRのmergeだけでは、現在有効なWorkflow、Issue Form、契約テスト、repository label、open Requirement Issueを2状態契約へ切り替えない。

新契約は、現在有効なWorkflowと案内文書、Issue Form、契約テストを同じ契約へ更新し、open Requirement Issueとrepository labelの外部移行結果を確認できた時点で有効化する。それまでは`docs/ai-development/workflows/requirement-lifecycle.md`が定める4状態契約を現在の規則として扱い、この設計判断記録だけを根拠に旧状態を無視しない。

GitHub上で実際に使用されるIssue Formは既定branch `main`の内容である。開発作業のbaseである`develop`上の変更だけを、liveなIssue Formの反映完了として扱わない。`develop`から`main`への反映は既存どおり人間が管理し、反映前後ともAIはラベルなしのIssueを作業開始可能と扱わない。

## 2状態のステータス契約

| 有効なステータス | 長時間状態として示す作業主体 |
|---|---|
| `AI：作業可能` | 現在のチャット指示を受けたAIが、永続成果物から復元した作業を進められる |
| `人間：PR確認待ち` | 完成したRequirement Analysis PR、設計PR、またはIssue統合PRを人間が確認する |

`人間：要求承認待ち`と`人間：タスク承認待ち`を新たな廃止対象とする。以前からの廃止対象である`人間：要求分析承認待ち`、`人間：基本設計承認待ち`、`人間：最終成果物承認待ち`も旧状態として扱う。これら5種類の旧状態、ステータス未付与、複数状態の競合は作業可能を意味しない。

ステータス以外のラベルは2状態の集合に含めず、併用できる。ラベルは要求、設計、Task計画、Pull Requestのmerge、review、verification、CI、受入条件充足の証拠を置き換えない。

## 初期状態とAI作業開始ゲート

AIがRequirement Issueを作成するときはステータスを付与せず、Issue Formも初期ステータスを付与しない。人間は要求原文と補足を確認し、作業開始を認める場合だけ`AI：作業可能`を付与する。

Mainは成果物、コメント、branch、Pull Request、ラベルを変更する前に最新Issueを取得し、次の両方を満たす場合だけRequirement Issueの工程作業を開始する。

- ステータス集合が`AI：作業可能`の1種類だけである。
- 人間から対象Issueと作業を示す現在のチャット指示がある。

AIによるIssue作成、Issue Formの送信、過去のチャット指示、ラベル変更だけでは開始しない。AIは自ら`AI：作業可能`を付与して作業権を取得しない。初期未付与、旧状態、競合、永続成果物との矛盾では、確認した状態と必要な人間対応を返して安全停止する。

## 工程復元と遷移

~~~text
AIがRequirement Issueを作成（ステータスなし）
  -> 人間が要求原文と補足を確認
  -> 人間がAI：作業可能を付与 + 現在のチャットで作業指示
  -> AIが永続成果物から現在工程を復元
  -> 必要な人間判断は同じチャットで質問・回答
  -> 回答後は同じチャットで作業継続
  -> 人間確認対象のPull Request完成
  -> 人間：PR確認待ち
  -> 人間がPull Requestを確認・merge
  -> 次工程へ進める場合、人間がAI：作業可能を付与 + 新しいチャット指示
~~~

要求分析書、設計判断記録、Task記録の有無だけで完了を推測せず、それぞれのPull Requestのmerge状態、実際のdiff、review、verification、CIを直接確認する。工程を一意に復元できない場合は未承認工程を飛ばさない。

### 工程途中の人間判断

要求分析、設計影響確認、Task Planning、実装中に未確定な要求、設計、計画、承認scopeがある場合は、選択肢と影響を同じチャットで質問する。質問中は`AI：作業可能`を維持する。人間の回答は質問で特定した事項の確定判断として永続成果物へ必要十分に反映し、同一事項の再承認や別チャットでの再開を求めない。

Task計画は現在どおり人間の確認対象とするが、GitHub上の`人間：タスク承認待ち`へ遷移しない。計画を同じチャットで提示し、人間の回答後は別の未確定判断または安全停止条件が生じない限り、承認済み計画に従うTask着手と実装へ同じチャットで進む。未着手計画をGitへ保存しない境界と、scope変更時に再計画して人間判断へ戻る境界は維持する。

### 正式な引き渡し

Requirement Analysis PR、設計PR、Issue統合PRのうち、人間が確認できる完成成果物を提出した場合だけ`人間：PR確認待ち`へ切り替える。Task PR、質問、計画提示、CI待ち、review中などの中間操作ではステータスを変更しない。

正式な引き渡しでは最新Issueを再取得し、非ステータスラベルを保持したまま、以前のステータスを`人間：PR確認待ち`だけへ置き換え、再取得して確認する。同じ作業指示では次工程へ進まない。Pull Requestのmerge、branch削除、Requirement Issueのcloseは人間だけが行う。

### PR確認待ち中の明示的な依頼

`人間：PR確認待ち`中でも、人間が現在のチャットで対象Pull Requestの修正、追加review、検証、説明などを明示的に依頼した場合は、その範囲だけを扱える。この例外は、Pull Requestがmerge済みであると推測することや、次工程へ進むことを許可しない。

依頼された対応の完了後も、対象Pull Requestが人間の確認対象である間は`人間：PR確認待ち`を維持する。依頼内容が次工程、要求変更、設計変更、または別scopeへ広がる場合は、現在の永続状態と必要な承認境界を確認する。

## 責務境界と依存方向

| 対象 | 変更後に所有する責務 | 所有しない責務 |
|---|---|---|
| `AGENTS.md` | 正本、現行証拠、承認scope、人間判断、品質、安全、能力発見の安定原則 | ステータス名、状態遷移、工程順序 |
| Requirement Issue lifecycle | 2状態、初期未付与、開始ゲート、工程復元、途中判断、正式引き渡し、停止・再開 | 個別能力の処理、共有判断基準の詳細 |
| `overview.md` | ステータスが現在の作業主体だけを示すことと、Workflowへの案内 | 状態遷移の詳細 |
| Issue Form | AIが作成した新規Issueへ初期ステータスを付与しないこと | 作業開始、状態遷移、自動実行 |
| Taskと提出のWorkflow | 承認済み計画、Task記録、二階層PR、Task PRで状態を変えない境界 | Requirement Issueの状態機械 |
| Skill | 入力された単一能力の結果 | ステータス変更、工程復元、次工程、提出判断 |
| Reference | 複数能力で共有する非実行の判断知識 | ステータス変更、工程制御 |
| Agent定義 | 役割と実行設定 | Workflow固有の状態と工程順序 |
| 契約テスト | activeな2状態と安全・品質境界の継続検知 | ラベルや工程完了の正本 |

依存方向は、現在の人間指示とGitHub上の最新Issueおよび永続成果物からRequirement Issue lifecycleへ向かい、Workflowから必要能力とReferenceへ向かう。Skill、Reference、Agent定義からWorkflowの状態遷移を要求しない。

## 外部状態の移行設計

### 移行対象

- repository label定義のうち、新たな廃止対象となる`人間：要求承認待ち`と`人間：タスク承認待ち`。以前に廃止済みと記録された3種類も、残存が判明した場合は対象へ戻す
- 実移行時点でopenのRequirement Issueに付与された5種類の旧状態、ステータス競合、または未付与
- activeなWorkflow、案内文書、Issue Form、契約テスト

過去の要求分析書、設計判断記録、完了Task記録は移行対象にしない。closed Issueは個別の状態移行対象にしないが、repository label定義の削除によって現在のlabel付与が除かれる場合もGitHubのlabel event履歴は保持されることを確認する。

### 移行判定

open Requirement Issueごとに、Issue、merge済みPull Request、要求分析書、設計判断記録、Task記録、実装、review、verification、CIを確認する。完成した人間確認対象PRが未mergeなら`人間：PR確認待ち`を移行候補とする。既に`AI：作業可能`の1状態だけで整合しているIssueはその状態を維持する。

旧状態、競合、未付与から`AI：作業可能`へ移す場合は、永続成果物から候補を提示できても、人間の明示判断なしに更新しない。対象PR、承認済みscope、現在工程を一意に判断できないIssueも自動移行せず、人間判断が得られるまで未移行として残す。移行のためにAIが自ら`AI：作業可能`を選び、作業権を取得してはならない。

### 整合性と復旧

- 移行前に対象Issue、変更前ラベル、非ステータスラベル、判定根拠、移行候補を記録する。
- Issue更新では非ステータスラベルを保持し、有効なステータス1種類だけへ置き換える。
- 各更新後と全体完了後にIssueを再取得し、変更前後、未移行、失敗を確認する。
- 部分失敗時は成功扱いにせず、削除前なら記録した変更前ラベルへ復旧できる状態を維持する。
- repository label定義の削除は、open Requirement Issueの移行と検証が完了し、旧ラベルを参照するliveなIssue Formがないことを確認した後に行う。
- GitHub連携でlabel定義を列挙・削除できない場合は、人間が削除対象を確認して操作し、その結果を移行記録へ残す。確認不能を削除成功として扱わない。

GitHubにはlabelを履歴専用として選択不能にする仕組みがないため、`人間：要求承認待ち`と`人間：タスク承認待ち`は名前変更や保持ではなく削除する。以前に廃止した3種類が残存していた場合も同様に削除する。削除前のIssue移行と記録を回復手段とし、削除後に契約全体を戻す必要が生じた場合のlabel再作成は人間が判断する。

## 検証設計

共通品質ゲート`sh scripts/verify.sh`とCI入口は変更しない。状態契約テストでは少なくとも次を確認する。

- activeなステータス表が`AI：作業可能`、`人間：PR確認待ち`の順で重複なく2種類だけである。
- `人間：要求承認待ち`、`人間：タスク承認待ち`を含む旧5状態がactiveな契約やIssue Formで使用されず、残存時は安全停止する。
- Issue Formが初期ステータスを付与しない。
- 開始には`AI：作業可能`の1状態と現在のチャット指示の両方が必要であり、AIによる自己付与とラベル単独起動を禁止する。
- Task計画の質問・確認は同じチャットで完結し、別ステータス、別チャット指示、同一事項の再承認を要求しない。
- Requirement Analysis PR、設計PR、Issue統合PRだけが正式な`人間：PR確認待ち`への引き渡し点であり、Task PRでは状態を変更しない。
- Worker、Reviewer、個別Skill、Reference、Agent定義が状態機械を所有しない。
- GitHub ActionsへIssue起動、ラベル起動、自動merge、自動closeを追加しない。
- 歴史的な要求分析書、設計判断記録、完了Task記録をactive契約の文字列検査対象として誤って書き換えない。

外部検証では、実移行時点のopen Requirement Issueについて、移行対象、変更前後、非ステータスラベルの保持、未移行、失敗、最終状態を確認する。repository label一覧をGitHub連携から取得できない制約が続く場合は、人間による削除確認を証拠として区別し、未確認事項と残るリスクをIssue統合PRへ記録する。

## 現在有効な設計正本への反映

この設計PRでは目標設計を`docs/design-decisions/67.md`へ記録し、現在有効な4状態契約や外部状態は変更しない。設計PRの人間merge後、後続の実装境界で次を同じ2状態契約へ整合させる。

- Requirement Issue lifecycleと`overview.md`
- Requirement Issue Form
- 状態契約テスト
- open Requirement Issueとrepository labelの外部状態

`AGENTS.md`、Taskと提出のWorkflow、成果物作成パターン、Reference、個別Skill、Agent定義、application code、application test、CI構成は現時点で新しい責務変更を必要としない。実装時にactiveな正本を再確認し、矛盾が生じた場合だけ承認済み設計の範囲で扱う。

要求範囲と基本設計に必要な未回答の人間判断はない。実移行時点で状態を一意に復元できないopen Requirement Issueが見つかった場合は、対象ごとの人間判断が必要である。

## 残るリスク

- repository label一覧とlabel定義の削除結果を現在のGitHub連携から直接確認できないため、人間の操作結果を外部証拠として区別して記録する必要がある。
- `develop`のIssue Form変更は既定branch `main`へ反映されるまでliveにならない。反映前に作成された未付与Issueを、AIが作業可能と誤認しない開始ゲートが必要である。
- 実移行までにopen Issue、Pull Request、ラベルが変化しうるため、設計時snapshotを移行対象として固定せず直前に再取得する必要がある。
- Task計画の質問中も`AI：作業可能`を維持するため、ラベルは会話の瞬間的な発話順ではなく長時間の作業主体を示すことをWorkflowと契約テストで一貫して扱う必要がある。
- 旧labelを削除する前にactiveな文書、Issue Form、open Issueの整合を確認しないと、一時的に開始・引き渡し不能となる可能性がある。
