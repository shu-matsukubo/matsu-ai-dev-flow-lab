## 設計結果

Skillの新規設計、既存Skillの変更、責務の分割・統合・削除、および設計レビューを一つの観点で評価するrepository管理下のメタSkillを、`.agents/skills/design-skill/SKILL.md`として追加する。このSkillは成果物を実装する能力やWorkflowを進める能力ではなく、入力された能力要求またはSkill定義を、自己完結性、依存方向、責務配置、共有知識、変更影響へ照合し、設計案またはfindingを返す読み取り評価能力とする。

詳細なSkill設計原則と判断方法はこのメタSkillが所有する。`AGENTS.md`には、Skillを自己完結した単一能力として設計すること、Skill間の直接依存を避けること、工程制御をWorkflowへ、共有判断知識をReferenceへ分離すること、およびSkillの新規設計・変更・レビュー時に利用可能な設計ガイドを能力契約から選択して確認することだけを安定原則として追加する。個別Skill名、具体的な禁止例、判定手順、固定Skill一覧は`AGENTS.md`へ置かない。

現行Skill群にはIssue #68の原則に対する明確な違反を確認できなかったため、新しいメタSkill以外の既存Skill本文は変更しない。設計時と実装完了時の全対象確認結果は、それぞれ設計判断記録と完了Task記録へrevision付きのsnapshotとして残す。これらは履歴的な監査証拠であり、runtime registryまたは更新対象の固定Skill一覧として扱わない。

継続検知は、activeな`.agents/skills/*/SKILL.md`を動的に発見し、front matter、Markdown section、runtime上のSkill識別子、依存を示す文脈を区別する専用契約テストで行う。自己宣言、一般的な能力または成果物の表現、Referenceと安定したrepository contractへの参照、禁止事項を説明する記述を許可する肯定経路と、別Skill識別子・具体path・呼び出し、前後工程要求、Workflow状態遷移の所有、設計ガイドの固定一覧を拒否する否定経路をfixtureで確認する。

## 適用境界

この設計PRでは目標設計を`docs/design-decisions/68.md`へ記録するだけで、現在有効なSkill、`AGENTS.md`、Workflow、Reference、契約テスト、application code、外部状態を変更しない。

設計PRの人間merge後、後続の承認済みTaskで、メタSkill、`AGENTS.md`、Skill設計契約テスト、およびテスト入口を同じ変更境界へ反映する。メタSkillまたは`AGENTS.md`だけを先行して有効化し、設計原則を検知できない期間や、検査だけが先行して現行Skillを不当に失敗させる期間を作らない。

設計判断記録は後続実装の根拠であり、それ単独でSkill設計ガイドを利用可能にせず、Task着手、Issue状態、Pull Request状態、承認scopeを変更しない。

## 目標責務と依存方向

~~~text
人間の現在の指示 + 永続状態
  -> Workflowが現在工程と必要能力を決定
      -> Skillの新規設計・変更・設計レビューが対象なら
          runtimeのdescriptionと能力契約から設計ガイドを選択
          -> 入力された能力要求、候補定義、安定したcontractを評価
          -> 設計案またはfinding、未確定事項、remaining riskを返す
      -> Workflowが結果を確認し、作成、修正、review、verification、提出を構成
~~~

設計ガイドから他Skillを呼び出さず、次に実行する能力、工程遷移、担当Agent、成果物変更、提出可否を決定しない。設計ガイドの入力にReferenceまたはrepository contractが必要な場合も、特定の別Skillを経由せず、判断に必要な内容または識別可能な安定した正本として受け取る。

## メタSkillの能力契約

### 識別と配置

- directoryとfront matterの`name`は`design-skill`とする。
- `description`は、新規設計、変更、分割・統合・削除、設計レビュー、疎結合、責務配置を対象に含むことを意味で識別できるようにする。
- Workflow、`AGENTS.md`、overview、Referenceへ`design-skill`という識別名を記載しない。実行時に提示される`name`と`description`から候補を選び、本文契約を照合する。
- repository管理外のSkillや固定catalogへ登録しない。

### 提供能力と適用条件

一つの能力は、入力されたSkill設計対象について「他Skillを知らなくても単独能力として成立し、正しい層へ責務が置かれているか」を評価し、必要なら設計案を返すことである。新規設計、既存定義の変更、分割・統合・削除、レビューは、いずれも同じ不変条件への評価形態として扱い、別工程を内包しない。

少なくとも次の入力を必要とする。

- 対象能力の目的、利用条件、期待する入力と出力
- 新規の場合は候補となる能力境界、既存の場合は現在の定義または固定revisionと変更目的
- 適用するrepositoryの安定原則、Workflow責務、Referenceまたはrepository contract
- 評価対象、対象外、承認scope

入力された固定Skill一覧、特定の前後Skill、特定Workflowの工程番号は成立条件にしない。

### 出力

- 対象の目的と単一能力としての境界
- 提供能力、適用条件、入力、出力、責務外、固有処理、失敗・未実施・不確実時の扱いからなる能力契約案または評価結果
- Skill、Workflow、Reference、`AGENTS.md`、履歴的成果物の配置判定と根拠
- 直接依存、工程依存、状態所有、共有知識の競合重複に関するfinding
- 分割、統合、維持、削除の判断案と比較案
- 変更が必要な対象と、変更不要な対象
- 未確定な人間判断、未確認事項、remaining risk

出力は設計案またはレビュー結果であり、file変更、承認、実装、他能力の実行、工程遷移、提出結果を意味しない。

### 責務外

- Skill、Workflow、Reference、`AGENTS.md`その他成果物の作成または変更
- Workflow選択、能力の組み合わせ、実行順序、停止・再開、状態遷移
- 別SkillまたはAgentの呼び出しと、その成功を成立条件にすること
- Task分解、実装、通常の成果物review、verification、submission
- 要求、設計、承認scope、最終判断の人間に代わる確定
- 固定Skill registry、手書きcatalog、既存Skill一覧の所有

### 設計判断の不変条件

1. 対象Skill単体から、提供能力、適用条件、入力、出力、責務外、固有処理、失敗・未実施・不確実時の扱いを判断できる。
2. 対象Skillは別Skillの名前、path、内部仕様、存在、呼び出し、出力取得、成功を成立条件または処理手順にしない。
3. 必要な前提や利用可能な結果は、特定Skillではなく入力となる成果物の性質または能力契約で表す。
4. 対象Skillは特定の前工程・後工程、工程番号、次の能力、Workflowの停止・再開・状態遷移を所有しない。
5. 一つの独立した結果と失敗境界を持つ能力だけを所有し、能力の構成と順序はWorkflowへ残す。
6. 複数能力で共有する判断基準、規約、形式は、競合するコピーを作らずReferenceまたは安定したrepository contractを正本にする。
7. repository全体で常に守る不変な原則だけを`AGENTS.md`へ置き、具体例、詳細基準、個別能力情報を置かない。
8. 変更対象は明確な違反または能力変更がある範囲へ限定し、履歴的成果物をactive contractとして書き換えない。

### 評価手順と代表例

メタSkillは、対象の目的と期待する結果を一文で固定し、7つの能力契約section、依存、工程制御、共有知識、変更波及の順に評価する。各findingは、対象箇所、違反する不変条件、具体的な影響、推奨する配置または表現、未確定事項を示す。表記の好みだけをfindingにせず、違反がない場合も確認範囲とremaining riskを返す。

実装するメタSkillには、少なくとも次の違いを一般化した例として含める。`<別能力>`や`<共有基準>`は説明用のplaceholderであり、現行Skill名のcatalogにしない。

| 判定 | 記述例 | 理由または置き換え方 |
|---|---|---|
| 禁止 | この処理後に`<別能力>`を呼び出す | 後工程と別能力の存在を前提にするため、能力の構成と順序はWorkflowへ置く |
| 禁止 | `<別能力>`の出力取得または成功を成立条件にする | 特定能力ではなく、必要な成果物の性質と不足時の扱いを入力契約へ記載する |
| 禁止 | Skill自身がWorkflow状態を更新し、次工程を開始する | 停止・再開・状態遷移はWorkflowへ置く |
| 禁止 | 現行Skill名とpathの一覧をガイド本文に保持する | runtime discoveryで能力契約から選択し、固定catalogを作らない |
| 許可 | レビュー結果が入力として与えられている場合は利用する | 特定能力ではなく成果物の性質へ依存している |
| 許可 | `<共有基準>`をReferenceまたは安定したrepository contractから入力する | 変化しやすいSkill間ではなく、一意な共有知識へ依存している |
| 許可 | 別能力の呼び出し、作業順序、状態遷移は責務外と記載する | 依存を要求せず、能力境界を否定文脈で明確にしている |

メタSkill自身も同じ不変条件で自己評価できることを契約へ含め、具体例の禁止文を実行手順として解釈しない文書構造にする。

### 配置判定

| 記述の性質 | 所有先 | 判定の要点 |
|---|---|---|
| 一つの能力の成立条件、入力、変換・評価、出力、固有の失敗境界 | Skill | 別能力なしでも独立した結果を返せる |
| 能力の選択と組み合わせ、順序、担当構成、承認、停止・再開、状態遷移 | Workflow | 複数能力または工程全体を制御する |
| 複数能力で共有する判断基準、規約、形式、禁止事項、例 | Reference | 処理を実行せず、共有知識を一意に保つ |
| repository全体で長期に安定して守る正本、scope、人間判断、品質、安全、発見原則 | `AGENTS.md` | 詳細手順や個別識別子を持たない |
| 特定時点の設計理由、監査結果、実施証拠 | 設計判断記録またはTask記録 | activeなregistryや将来の更新対象にしない |

### 分割・統合・削除の判断

- 独立した出力、適用条件、権限、mutation、失敗境界、再利用理由を持つ責務は分割候補にする。
- 一方の能力がなくても他方が意味のある結果を返せる場合、前後工程として一つのSkillへ統合しない。
- 常に同じ目的、入力、出力、失敗境界を共有し、分割後に単独で意味を持たない記述は統合候補にできる。
- 固有の能力を持たずWorkflow制御だけを包むSkill、別の安定した能力契約で完全に代替されるSkill、利用要求が失われたSkillは削除候補にする。
- 分割、統合、削除によって要求、public contract、承認scope、運用概念が変わる場合は、設計ガイドだけで確定せず人間判断へ返す。

## `AGENTS.md`の変更境界

`AGENTS.md`の「作業原則」へ、一つの段落で次の安定原則を追加する。

- Skillは自己完結した単一能力として設計する。
- Skill間の直接依存を避ける。
- 工程制御はWorkflow、共有判断知識はReferenceへ分離する。
- Skillの新規設計・変更・レビューでは、その時点で利用可能なSkill設計ガイドを能力契約から選択して確認する。

追加文には、メタSkillの`name`、directory、固定Skill一覧、具体的な禁止例、判定正規表現、section別の詳細手順、分割・統合・削除の詳細基準を含めない。既存の正本、承認scope、人間判断、品質、提出、安全、専門レビューの安定原則は変更しない。

## Workflow、Reference、overviewの変更境界

新しいWorkflowは追加せず、現行Workflow本文も変更しない。Skill設計はRequirement Issue lifecycleやTask実装など既存工程の対象になり得るが、どの工程で何を作るかは現行Workflowが既に能力の意味と入出力から選択できる。メタSkillへ工程制御を追加せず、Workflowへ個別Skill名を追加しない。

新しいReferenceは追加せず、現行Reference本文も変更しない。詳細なSkill設計判断はメタSkill自身の固有処理であり、複数の独立能力が共有する非実行知識として別正本へ分割すると、メタSkill単体では意味が分からない構造と二重管理を生む。既存のレビュー、検証、Task分解、提出、安全、Flow Feedback基準は必要に応じて入力できる安定したcontractとして維持する。

`overview.md`も変更しない。責務分離、依存方向、runtime discovery、固定registryを作らない原則は既に必要十分であり、個別の設計ガイドを案内すると手書きcatalogを再導入する。利用の安定した入口は要求どおり`AGENTS.md`だけに追加する。

## 継続検知の設計

### 検証対象

- activeな`.agents/skills/*/SKILL.md`
- Skill設計に関する安定原則を保持する`AGENTS.md`
- runtime discoveryと責務分離を保持する`overview.md`およびWorkflow
- 新しいメタSkillを意味で選択するfixture

要求分析書、設計判断記録、完了Task記録、過去IssueやPull Request本文は、当時の判断や旧識別子を保持する履歴であり、active Skill依存の検査対象にしない。

### 文書を解釈する検査

専用の`tests/skill-design-contract.test.mjs`を追加し、既存テストと同じくdirectoryを列挙してSkillを動的に発見する。検査は少なくとも次を区別する。

1. front matterの`name`と`description`は自己宣言として扱い、directoryとの一致と一意性を確認する。
2. 本文をMarkdown sectionへ分け、7つの能力契約があり、各sectionに意味のある内容があることを確認する。
3. 現在発見した他Skillの識別子、`$`形式の識別子、具体的なSkill directoryまたは`SKILL.md` pathを直接依存候補として検出する。
4. 適用条件と固有処理で、前後工程または別能力の実行を要求する文と、Skill自身がWorkflowの停止・再開・状態遷移を実行または決定する文を検出する。
5. `責務外`や設計ガイド内の禁止説明は、依存または工程所有を否定する文脈として区別する。単語の出現だけで違反にしない。
6. メタSkillは`name`ではなくdescriptionと能力契約から一意に選択し、他の発見済みSkill識別子や固定一覧を本文に持たないことを確認する。
7. 既存の追加・名称変更・削除fixtureで、操作対象外のSkill、メタSkill、`AGENTS.md`が不変で、runtime discoveryだけで結果集合が更新されることを確認する。

### 肯定経路fixture

次の記述を持つ自己完結したSkillを受理する。

- front matterによる自分自身の`name`宣言
- 「レビュー結果が入力として与えられている場合は利用する」など、成果物の性質による入力契約
- 「別能力の呼び出しや作業順序の決定は責務外」のような禁止境界
- Referenceまたは安定したrepository contractを入力として参照する記述
- 一般語としてのSkill、Workflow、review、verification、submission

### 否定経路fixture

それぞれ独立したfixtureで、少なくとも次を拒否する。

- 発見済みの別Skill名またはその具体pathを適用条件や固有処理へ記載する
- `$<skill-name>`形式で別Skillを呼び出す
- 別Skillの出力取得または成功を成立条件にする
- 「完了後に次のSkillを実行する」など前後工程を要求する
- Skill自身がWorkflow状態を変更し、停止・再開・次工程を決定する
- メタSkillが現行Skill名の一覧を保持する

検査関数自体のUnit Testとして肯定・否定fixtureを実行し、repositoryの実Skillに対する検査と同じpredicateを使用する。単純な禁止語検索だけを別実装で追加しない。

### 既存テストとの関係

- `tests/requirement-status-contract.test.mjs`の状態、Workflow、Reference、追加・名称変更・削除に関する既存検査は維持する。
- `tests/expert-review-contract.test.mjs`の専門レビュー能力と名称変更fixtureは維持する。
- root `package.json`の`test`へ新しい契約テストを追加し、共通品質ゲートとCIから必ず実行する。
- 既存テストの大規模な共通helper化やfile renameはこのIssueの目的に必要ないため行わない。

## 実装時の監査記録

実装Taskの完了記録には、検証対象revision、動的に発見した全Skill、各Skillの結果、finding、変更有無と理由を残す。最低限、次を区別する。

- 自己完結した能力契約: 適合 / finding
- 別Skill識別子・path・存在への依存: なし / finding
- 前後工程要求とWorkflow状態所有: なし / finding
- 共有知識の競合する重複: なし / finding
- 変更: あり / なし、および根拠

新しいメタSkillも監査対象に含める。設計時点で適合した既存Skillは、実装時の最新revisionで再確認し、明確な違反または設計時点からの変更がなければ編集しない。完了記録はsnapshotであり、将来のSkill追加時に更新するregistryにはしない。

## 移行順序と整合条件

後続実装では、同じTaskと変更treeで次を行う。

1. 最新の正本と全Skillを再取得し、設計時監査との差分を確認する。
2. メタSkillを追加し、単体の能力契約と詳細な設計判断を記載する。
3. `AGENTS.md`へ安定原則と利用入口だけを追加する。
4. 専用契約テストと肯定・否定fixtureを追加し、既存の追加・名称変更・削除fixtureをメタSkill不変性まで拡張する。
5. 全Skillを同じpredicateと人間による共有知識確認へ照合し、明確な違反だけを修正する。
6. 完了Task記録へ対象revision、全件結果、変更理由、未確認事項、remaining riskを残す。
7. 共通品質ゲートと変更リスク固有の契約テストを実行する。

次のすべてが一致した時点で新しい設計契約を有効とみなす。

- runtime discoveryからメタSkillを意味で一意に選択できる。
- `AGENTS.md`が安定原則と利用入口だけを持つ。
- activeな全Skillが自己完結し、別Skillと工程へ直接依存しない。
- Workflow、Reference、overviewの現在責務に不要な変更がない。
- 肯定・否定fixture、追加・名称変更・削除fixture、既存契約テスト、共通品質ゲートが成功する。
- 全対象監査、未実施項目、remaining riskを完了Task記録から追跡できる。

## 残るリスク

- 自然言語だけから工程所有を完全に判定することはできない。構造と文脈を使うpredicate、否定fixture、人間による全件監査を組み合わせ、テスト成功だけを設計妥当性の完全保証にしない必要がある。
- 現在発見できない削除済みSkill名や巧妙な言い換えはruntime識別子照合だけでは検出できない。具体pathと呼び出し文脈の検査、メタSkillによる設計レビューで補う必要がある。
- `責務外`の禁止説明や設計ガイド自身の違反例を単純一致すると誤検出する。sectionと肯定・否定文脈を同じpredicateで検証し、例外の無制限なallowlistを作らない必要がある。
- 詳細なSkill設計知識をメタSkillが所有するため、そのSkill自体の変更で判断基準が弱まる可能性がある。自己適用の契約テストと、変更時の設計レビューを維持する必要がある。
- 設計時監査後に現行Skillが変わる可能性があるため、実装Taskでは最新revisionの全件監査を再実行し、設計時snapshotだけで変更不要と判断しない。
- built-inまたはrepository管理外のSkillは対象外であり、このrepositoryの契約テストではその疎結合性を保証しない。
