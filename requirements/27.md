# Issue #27 要求分析

## 元Issue

- [Issue #27: Requirement Issueと要求分析を分離し、人間の思考過程を保持する要求分析フローを導入する](https://github.com/shu-matsukubo/matsu-ai-dev-flow-lab/issues/27)
- 承認済み設計: [PR #28: 要求分析の正本と承認境界を導入する](https://github.com/shu-matsukubo/matsu-ai-dev-flow-lab/pull/28)

## 目的

AI駆動開発の速度を維持しながら、要求から要求分析へ至る重要な判断について、人間が探索・比較・棄却・理由付けへ参加したことを追跡できる状態にする。

Requirement Issueを分析前の入力、要求分析書を分析結果の正本、Requirement Analysis PRを人間の承認境界として分離し、完成した成果物だけを後から承認する運用から、重要な思考過程と判断根拠を確認できる運用へ移行する。

## 要件

### RQ-01 Requirement Issueの責務

- Requirement Issueは「要求【必須】」と「補足【任意】」を中心とする。
- 「要求」には要求者から受け取った要求原文を、AIによる要約や解釈へ置き換えず、原則として内容を変えずに記録する。
- 「補足」にはIssue登録前の壁打ちで得られた背景、意図、優先順位、検討案、採用・棄却理由、懸念、未確定事項などを自由記述で残せる。
- 補足を完成された仕様書として整形することを要求せず、補足なしでもIssueを登録できる。
- Requirement Issue自体は要求分析の正本にしない。

### RQ-02 要求分析書

- Issue登録後にCodexがIssueの要求と補足を入力として、要求分析書をGit管理ファイルとして作成する。
- 要求分析書は、元Issue、目的、要件、受入条件、制約、対象外、重要な人間判断と根拠、未確定事項、確認履歴を記録できる。
- 受入条件の正本は要求分析書とする。
- 要求分析書を実装進捗の記録場所として更新しない。

### RQ-03 探索と人間判断

- 要求分析をIssue本文の単純な整形や言い換えにせず、必要に応じて前提、解釈候補、複数案、利点・欠点、影響、トレードオフを整理する。
- AI自身の提案や推測を、人間が判断済みの事項として扱わない。
- 要求範囲や受入条件の確定に人間判断が必要で、Issueの補足から判断を確認できない場合は、要求分析を確定する前に必ず人間へ質問する。
- 要求分析中の質問、回答、確定した判断を、チャット全文ではなく必要十分な確認履歴として要求分析書へ残す。
- Issue登録前の思考材料である「補足」と、要求分析中に発生した「確認履歴」を別の正本として扱う。

### RQ-04 承認境界とチャット境界

- 要求分析書を最新のdevelopをbaseとする専用のRequirement Analysis PRで公開する。
- 人間がRequirement Analysis PRを確認してmergeするまで、設計影響確認へ進まない。
- merge後は要求分析チャットを終了し、別チャットでRequirement Issue、merge済み要求分析書、最新develop、最新docsを読み直して設計影響確認を開始できる。

### RQ-05 後続フロー

- Requirement Analysis PR merge後の設計影響確認、必要な場合のDesign PR、Task Planning、Issue branch、Task PR、Issue Integration PRという既存の基本フローを維持する。
- 要求分析と設計判断、設計と実装計画の責務境界を統合しない。

### RQ-06 受入確認とIssue完了

- 最終Issue Integration PRで、要求分析書の受入条件を1件ずつ確認し、結果と根拠となるTask PR、実装、テスト、検証結果を記録する。
- Requirement Analysis PR、Design PR、Task PR、Issue Integration PRではRequirement Issueを非close形式で参照する。
- PR mergeでRequirement Issueを自動closeせず、merge済み統合PRの受入確認を参照した人間だけが任意のタイミングで明示的にcloseする。

### RQ-07 運用全体の整合性と品質

- AGENTS.md、AI開発フロー文書、関連Skill、Issue Form、PR運用を新しい責務境界へ整合させる。
- 既存の品質ゲートと、変更リスクに応じたTask固有検証を維持する。

## 受入条件

以下は要求達成の判定条件であり、この文書上のチェック状態を実装進捗として更新しない。Issue Integration PRで各IDの充足結果と根拠を記録する。

- AC-01: Requirement Issue Formが「要求【必須】」「補足【任意】」を中心とする入力構造になっている。
- AC-02: 「要求」に要求原文を内容を変えず記録する方針が維持されている。
- AC-03: 「補足」にIssue登録前の壁打ち、判断、理由、懸念、未確定事項などを自由に記録できる。
- AC-04: 補足なしで、要求だけでもRequirement Issueを登録できる。
- AC-05: Requirement Issue自体を要求分析の正本として扱わない構造になっている。
- AC-06: Requirement Issueから要求分析書をGit管理ファイルとして作成する工程が追加されている。
- AC-07: 要求分析書に元Issue、目的、要件、受入条件、制約、対象外、重要な人間判断、未確定事項、確認履歴を記録できる。
- AC-08: 要求分析時に、必要に応じて複数案、比較、トレードオフを検討する方針が定義されている。
- AC-09: AI自身の提案や推測を、人間が判断済みの事項として扱わないことが明記されている。
- AC-10: 人間判断が必要で未確定の事項は、要求分析を確定する前に必ず人間へ質問する。
- AC-11: 要求分析中の質問と回答が、必要十分な確認履歴として要求分析書へ残る。
- AC-12: Issueの補足と要求分析中の確認履歴の責務が分離されている。
- AC-13: 要求分析書を専用PRで作成し、人間がmergeするまで設計影響確認へ進まない。
- AC-14: Requirement Analysis PR merge後に要求分析チャットを終了し、別チャットから設計影響確認を再開できる。
- AC-15: 設計影響確認以降の既存Design、Task Planning、Task PR、Issue Integration PRフローが維持されている。
- AC-16: 受入条件の正本が要求分析書へ移行している。
- AC-17: 最終Issue Integration PRで、要求分析書の受入条件を1件ずつ根拠付きで確認する。
- AC-18: 要求分析書自体を実装進捗チェックリストとして不要に更新しない。
- AC-19: Issue Integration PRのmergeによってRequirement Issueを自動closeしない。
- AC-20: 人間がmerge済み統合PRの受入確認を参照し、任意のタイミングでRequirement Issueを明示的にcloseできる。
- AC-21: AGENTS.md、AI開発フロー文書、関連Skill、Issue Form、PR運用が新しい責務境界と整合している。
- AC-22: 既存の品質ゲートと必要なTask固有検証が成功する。

## 制約

- 人間へ新しい定型文書の手入力を求めず、壁打ち、必要な判断、承認を中心とする操作感を維持する。
- Requirement Issueの補足は任意とし、事前に十分な壁打ちをしていない要求も受け付ける。
- 要求分析で不足する人間判断をAIが推測して埋めることで工程を省略しない。
- Issue登録前の思考材料と、要求分析中の確認履歴を同じ正本へ混在させない。
- 要求分析と設計判断の責務を混在させない。
- Requirement Analysis PR、Design PR、Task PR、Issue Integration PRの承認境界を不要に統合しない。
- 個人情報、secret、credential、実案件固有情報、判断に不要な会話を要求分析書へ記録しない。
- GitHub Issueの自動closeを導入しない。
- Issueへの情報投影だけを目的とするCIや外部基盤を新設しない。

## 対象外

- Frontend、Backend、API契約、認証・認可・session、persistence、DB、runtime securityなど、アプリケーション実行時の設計変更。
- 既存のDesign、Task Planning、Task PR、Issue Integration PRの基本フロー自体の再設計。
- チャット全文を監査ログとしてGitへ保存する仕組み。
- CI、DB、scheduler、外部SaaSなどを使った要求情報の自動同期・自動集約。
- 完了済みIssueの遡及移行、および要求分析書がないopen Issueの一括移行。
- AI agentによるPull Requestのmerge、branch削除、Requirement Issueのclose。

## 重要な人間判断

| 判断対象 | 採用した判断 | 比較・棄却した案 | 根拠 |
|---|---|---|---|
| 要求と要求分析の正本 | Issueは要求原文と事前の補足、Git管理ファイルは要求分析の正本とする | Issue本文を引き続き要求分析の正本にする | 成果だけでなく、人間が参加した判断過程を追跡し、責務を明確に分けるため |
| Issueの補足 | 自由記述かつ任意とする | 完成した要求分析や定型文書の入力を必須にする | 人間は壁打ち・判断・承認へ集中し、構造化をAIが担うため |
| 要求分析中の確認 | 未確定の重要判断は人間へ質問し、必要十分なQA要約を確認履歴へ残す | AIが推測して確定する、またはチャット全文を保存する | 人間判断とAI提案を区別しつつ、不要・機密な会話の複製を避けるため |
| 要求分析の承認 | 専用Requirement Analysis PRを独立した承認境界とし、merge後に別チャットへ切り替える | Design PRと統合する、または同じチャットで設計へ連続して進む | 「何を満たすか」と「どの構造で実現するか」を分離するため |
| 受入条件と進捗 | 要求分析書を受入条件の正本とし、達成状況と根拠はIssue Integration PRへ記録する | 要求分析書のチェックリストを実装中に更新する | 要求定義と実装状態の正本を混在させないため |
| Issue完了 | どのPRでも自動closeせず、人間が統合PRの受入確認後に明示的にcloseする | Issue Integration PRのmergeで自動closeする | mergeと要求受入の判断を分離し、人間が最終確認を所有するため |

### PR #28で承認済みのブートストラップ設計

- 要求分析書は `requirements/<issue-id>.md`、共通構造は `requirements/TEMPLATE.md` とする。
- ファイル名にはIssue番号だけを使い、Issue title変更に伴うrenameを避ける。
- 要求分析は `$analyze-requirement` が担当する。
- 要求分析書が存在しないopen Issueは一括移行せず、次の後続工程へ進む前に要求分析とRequirement Analysis PRを通す。
- Issue #27自身については、上記templateとSkillを導入する実装前であるため、PR #28で承認された構造を直接適用してこの要求分析書を作成する。

## 未確定事項

- 要求範囲または受入条件の確定に必要な、未回答の人間判断はない。
- 具体的な変更箇所、文言、Task分割、検証方法は、merge済み設計の境界内で後続の設計影響確認とTask Planningが扱う実装上の事項であり、要求の未確定事項には含めない。

- この要求分析書のPRが人間によってmergeされるまで、設計影響確認へ進まない。

- 後続工程はAC-01からAC-22を正本として参照し、最終Issue Integration PRで1件ずつ充足結果と根拠を示す。
