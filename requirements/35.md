# Issue #35 要求分析

## 元Issue

- [Issue #35: ステータスラベルで人間とAIの承認ゲート・作業権を明示する](https://github.com/shu-matsukubo/matsu-ai-dev-flow-lab/issues/35)

要求原文とIssue登録前の補足は元Issueを参照し、この文書へ重複して正本化しない。

## 目的

Requirement Issueごとに、現在の作業権が人間とAIのどちらにあるか、人間が次に何を承認する必要があるかをGitHub上で判別できる状態にする。

Issueの登録や過去の作業指示だけを理由にAIが未承認の工程へ進むことを防ぎつつ、人間は単一の`AI：作業可能`ラベルとチャットの作業指示によって次のAI作業を許可できるようにする。工程の詳細は既存の永続情報から復元し、要求分析、基本設計、タスク、最終成果物の各承認ゲートを省略しない。

## 要件

### RQ-01 ステータスラベルと責務

- Requirement Issueの作業権と次の承認対象を表すステータスラベルとして、次の6種類を使用する。
  - `人間：要求承認待ち`
  - `AI：作業可能`
  - `人間：要求分析承認待ち`
  - `人間：基本設計承認待ち`
  - `人間：タスク承認待ち`
  - `人間：最終成果物承認待ち`
- ステータスラベルはRequirement Issueの詳細な工程状態をすべて表現する正本ではなく、現在の作業権と、人間が確認すべき次の承認対象を示す。
- 対象Issueのステータスラベルは定常状態で1種類だけとし、別のステータスへ進むときは以前のステータスラベルを残さず切り替える。ステータス以外のラベルとの併用は妨げない。

### RQ-02 新規Requirement Issueの初期状態

- Requirement Issueを新規登録したとき、`人間：要求承認待ち`を自動付与する。
- Issueが作成された事実だけではAIへ作業権を与えず、要求者が要求を確認するまでAI作業を開始可能な状態にしない。
- 自動付与の未完了または失敗によりステータスラベルが存在しない場合も、AIが作業可能であるとは扱わない。

### RQ-03 人間からAIへの作業権の移行

- 人間が現在の承認対象を確認した後、対象Issueのステータスを`AI：作業可能`へ切り替え、チャットで対象Issueに対する作業を指示する。
- `AI：作業可能`へのラベル変更とチャットでの作業指示の両方を、AIが作業を開始する条件とする。
- ラベル変更だけを契機としてAI作業を自動実行しない。
- AIは自ら`AI：作業可能`を付与して、未付与の作業権を取得しない。

### RQ-04 AI作業開始時のゲート

- AIは対象Requirement Issueの作業を開始するたびに、GitHub上の最新ステータスラベルを確認する。
- ステータスラベル集合のうち`AI：作業可能`だけが付与されている場合に限り、作業を開始する。
- 人間承認待ちラベルが付与されている場合、ステータスラベルがない場合、または複数のステータスラベルが競合している場合は作業を進めず、現在AIが作業可能な状態ではないことと確認した状態を報告して終了する。
- AI作業開始を拒否した場合は、成果物作成、工程進行、ステータスラベル変更を行わない。

### RQ-05 現在工程の復元

- AI側の作業可能ステータスは`AI：作業可能`の1種類とし、要求分析、基本設計、タスク、実装など工程別のAIラベルへ細分化しない。
- AIはRequirement Issue、merge済み要求分析書、merge済み設計、Pull Request、Task記録などの永続情報を読み直し、既存の承認境界に従って次に実施すべき工程を復元する。
- `AI：作業可能`ラベルだけを、成果物の承認、Pull Requestのmerge、または前工程の完了を示す証拠として扱わない。
- 永続情報とラベルが矛盾し、既存の承認境界を満たした工程を一意に復元できない場合は、未承認工程を推測で飛ばさず、不整合を報告して停止する。

### RQ-06 承認対象完成時の人間への引き渡し

- AIが現在工程の承認対象まで作業を完了したら、`AI：作業可能`を対応する人間承認待ちラベルへ切り替え、そこで作業を終了する。
- 要求分析書と専用Requirement Analysis PRを作成した後は、`人間：要求分析承認待ち`へ切り替える。
- 基本設計の内容または基本設計不要という判断を提示した後は、`人間：基本設計承認待ち`へ切り替える。
- 人間が承認可能なTask Planningを提示した後は、`人間：タスク承認待ち`へ切り替える。
- 承認済みTaskの実装、レビュー、Issue全体の統合・回帰検証、全受入条件の確認を終えた後は、`人間：最終成果物承認待ち`へ切り替える。
- 人間承認待ちへ切り替えた同じ作業指示の中で、次の工程を続行しない。

### RQ-07 基本設計ゲート

- 基本設計が必要な場合は、人間が設計内容を確認できる成果物を作成し、`人間：基本設計承認待ち`へ切り替えて終了する。
- 基本設計が不要と判断した場合も基本設計工程を暗黙に省略せず、その根拠をRequirement Issueへコメントし、`人間：基本設計承認待ち`へ切り替えて終了する。
- 基本設計不要と判断した同じ作業指示の中で、Task Planningへ進まない。
- 人間が設計内容または基本設計不要という判断を承認し、再び`AI：作業可能`へ切り替えて新たに作業を指示した後にだけ、後続工程へ進む。

### RQ-08 一時的な質問と既存フローの維持

- 要求分析などでAIから人間への確認が必要な場合は、質問と回答をチャット内で扱い、`人間：回答待ち`などの一時的なQA用ステータスラベルを追加しない。
- 一時的なQAのために正式な承認待ちステータスを流用せず、現在工程の承認対象が完成するまでは正式なステータス遷移を行わない。
- ステータスラベルの導入後も、Requirement Analysis PR、設計PR、Task PR、Issue統合PRの既存の承認境界、AIがPull Requestをmergeしない境界、AIがRequirement Issueをcloseしない境界を維持する。

## 受入条件

以下は要求達成の判定条件であり、この文書上の状態を実装進捗として更新しない。Issue統合PRで各IDの充足結果と根拠を記録する。

- AC-01: 指定された6種類のステータスラベルが、表記を変えずRequirement Issueで利用できる。
- AC-02: 対象Requirement Issueの定常状態ではステータスラベルが1種類だけとなり、遷移時に以前のステータスラベルが残らない。
- AC-03: 新規Requirement Issueに`人間：要求承認待ち`が自動付与され、Issue作成だけでは`AI：作業可能`にならない。
- AC-04: ステータスラベルが未付与の場合も、AIが作業可能な状態とは判定されない。
- AC-05: 人間が承認対象を確認して`AI：作業可能`へ切り替え、チャットで作業を指示した場合にだけ、AI作業を開始できる。
- AC-06: `AI：作業可能`へのラベル変更だけではAI作業が自動実行されず、AIが自ら同ラベルを付与して作業権を取得しない。
- AC-07: AIは作業開始ごとに最新ラベルを確認し、ステータスラベル集合のうち`AI：作業可能`だけが付与されている場合に限り作業を進める。
- AC-08: 人間承認待ち、ステータス未付与、または複数ステータス競合の場合、AIは確認した状態を報告し、成果物作成・工程進行・ラベル変更をせず終了する。
- AC-09: AIは工程別AIラベルを使用せず、Issue、merge済み成果物、PR、Task記録などの永続情報から次の工程を復元する。
- AC-10: ラベルと永続情報が矛盾して前工程の承認を確認できない場合、AIはラベルだけを根拠に未承認工程を飛ばさず、不整合を報告して停止する。
- AC-11: 要求分析書と専用PRの作成後、ステータスが`人間：要求分析承認待ち`へ切り替わり、設計影響確認へ続けず終了する。
- AC-12: 基本設計が必要な場合、設計の承認対象を提示した後に`人間：基本設計承認待ち`へ切り替わり、Task Planningへ続けず終了する。
- AC-13: 基本設計が不要な場合、判断根拠がRequirement Issueへコメントされ、`人間：基本設計承認待ち`へ切り替わり、Task Planningへ続けず終了する。
- AC-14: 基本設計に関する人間承認後、`AI：作業可能`への切り替えと新たな作業指示を経てTask Planningを行い、提示後は`人間：タスク承認待ち`へ切り替えて終了する。
- AC-15: Task承認後、`AI：作業可能`への切り替えと新たな作業指示を経て実装・レビュー・統合検証を行い、全受入条件の確認後は`人間：最終成果物承認待ち`へ切り替えて終了する。
- AC-16: 一時的な質問と回答はチャット内で扱われ、QA専用または工程別AIステータスラベルが追加されていない。
- AC-17: ラベル遷移によってPull RequestのmergeやRequirement Issueのcloseが自動実行されず、既存の人間承認境界が維持されている。
- AC-18: ステータスラベルの初期付与、遷移、AI開始ゲート、異常状態での停止について、既存の共通品質ゲートと変更リスクに応じた追加検証が成功する。

## 制約

- ステータスラベル名はIssue本文で指定された6種類を使用する。
- AI側のステータスは`AI：作業可能`の1種類だけとする。
- ステータスラベルに工程の詳細状態や一時的なQA状態を持たせない。
- AIが開始条件を確認できない場合は、安全側に停止する。
- 工程の完了と人間承認は、ラベルだけでなく既存の永続情報と承認済み成果物から確認する。
- ラベル変更だけを契機とするAI作業の自動実行を行わない。
- AI agentによるPull Requestのmerge、branch削除、Requirement Issueのcloseを行わない。
- 個人情報、secret、credential、実案件固有情報をラベル、コメント、成果物、作業記録へ追加しない。

## 対象外

- `人間：回答待ち`など、一時的な質問回答を管理するステータス。
- `AI：要求分析可能`、`AI：基本設計可能`など、工程ごとのAI作業可能ステータス。
- ラベルだけでPR、Task、merge状況などフローの全詳細を表現する仕組み。
- `AI：作業可能`への変更だけでAIを自動起動する仕組み。
- 過去に完了済みのRequirement Issueへのステータスラベルの一括遡及付与。
- ステータスラベルの色、説明文、Requirement Issueの機械的な識別方法、具体的なGitHub Actions構成、変更対象file、Task分割、検証コマンドの確定。
- Frontend、Backend、API契約、認証・認可、session、persistence、DBなど、アプリケーション実行時の機能変更。

## 重要な人間判断

| 判断対象 | 採用した判断 | 比較・棄却した案 | 根拠 |
|---|---|---|---|
| ラベルの責務 | 現在の作業権と次の人間承認対象を示し、詳細状態の正本にはしない | ラベルで全工程・PR・Task状態を表現する | GitHub UIで必要な判断を分かりやすくしつつ、既存の永続情報との二重管理を避けるため |
| 初期作業権 | 新規Requirement Issueは`人間：要求承認待ち`から開始する | Issue作成直後からAI作業を許可する | 人間が要求を確認する前にAIが処理を開始することを防ぐため |
| AIへの引き渡し | 人間が`AI：作業可能`へ切り替えた後、チャットで作業を指示する | ラベル変更だけでAIを自動起動する | 人間の操作を単純化しつつ、対象と依頼内容をチャットで明示するため |
| AI側ステータス | `AI：作業可能`の1種類に統一する | 工程ごとにAI作業可能ラベルを分ける | 人間のラベル操作を単純化し、工程は永続情報から復元できるため |
| 人間側ステータス | 要求、要求分析、基本設計、タスク、最終成果物の承認対象ごとに分ける | 人間承認待ちを1種類に統一する | GitHub UIだけでも次に確認すべき対象を識別しやすくするため |
| 基本設計不要の扱い | 根拠をIssueへコメントし、設計内容と同じ承認ゲートで人間確認を受ける | AI判断だけで設計工程を省略しTask Planningへ進む | 設計が不要という判断自体を承認対象とし、暗黙の工程省略を防ぐため |
| 一時的なQA | 質問と回答はチャット内で扱い、QA用ステータスを追加しない | `人間：回答待ち`を追加する | 正式な承認ゲートと一時的な質問回答を混在させないため |
