# Issue #67 要求分析

## 元Issue

- [Issue #67: ステータスラベルを「AI作業可能 / PR確認待ち」の2状態へ簡略化する](https://github.com/shu-matsukubo/matsu-ai-dev-flow-lab/issues/67)

要求原文とIssue登録前の補足は元Issueを参照し、この文書へ重複して正本化しない。

## 目的

Requirement Issueのステータスラベルを、工程ごとの進捗表ではなく、AIと人間のどちらが次に行動するかを示す最小限の作業主体表示へ簡略化する。工程途中の判断は進行中のチャット、完成成果物の確認はPull Requestへ集約し、既存の品質・承認・安全境界を維持したまま、ラベル切り替え、再依頼、状態整合の管理コストを減らす。

## 要件

### RQ-01 2状態のステータス契約

- Requirement Issueの通常フローで有効なステータスラベルを、`AI：作業可能`と`人間：PR確認待ち`の2種類だけにすること。
- ステータスラベルは現在の作業主体だけを示し、要求分析、基本設計、Task Planning、実装などの工程や、その工程の完了・承認を表す正本として扱わないこと。
- `人間：要求承認待ち`、`人間：タスク承認待ち`、その他の工程固有の承認待ちステータスを通常フローで使用しないこと。
- ステータス以外の用途を持つラベルは、2状態のステータス契約と区別して併用できること。

### RQ-02 AI作業の開始・停止条件

- AIがRequirement Issueの作業を開始できるのは、最新のIssueで`AI：作業可能`を確認し、かつ現在のチャットで人間から対象Issueと作業を示す指示を受けた場合だけとすること。
- `AI：作業可能`の付与だけを契機に作業を自動実行せず、AIが同ラベルを自ら付与して作業権を取得しないこと。
- `人間：PR確認待ち`の間は、明示的に依頼された別作業を除き、対象Pull Requestの人間確認前にRequirement Issueの次工程を自律的に進めないこと。
- ステータス未付与、旧ステータスの残存、複数ステータスの競合、または永続成果物との矛盾がある場合は、未承認工程を推測で進めず、確認した状態と必要な対応を人間へ返すこと。

### RQ-03 永続成果物による工程復元

- 現在工程と次に必要な作業は、Requirement Issue、merge済みPull Request、要求分析書、設計判断記録、Task記録、実装、review、verificationなど、その時点で有効な永続成果物から復元すること。
- ステータスラベルだけを、工程完了、成果物承認、Pull Requestのmerge、またはTask完了の証拠として扱わないこと。
- チャットで確定した重要な人間判断は、後続チャットが過去の会話だけに依存しないよう、該当工程の永続成果物へ必要十分に反映すること。

### RQ-04 工程途中の人間判断

- 要求分析、基本設計、Task Planning、実装などの途中で要求範囲、設計、または承認済みscopeに関する人間判断が必要になった場合は、進行中の同じチャットで選択肢と影響を示して質問すること。
- 人間の回答は、質問で特定した事項に対する確定済み判断として扱い、回答後に同一事項への再承認、承認待ちラベルへの切り替え、または新しい開始依頼を要求しないこと。
- 回答後は、別の未確定判断または安全停止条件が生じない限り、その工程で人間が確認すべき完成成果物の提出まで同じチャットで継続できること。

### RQ-05 完成Pull Requestでの正式な引き渡し

- Requirement Analysis PR、設計PR、Issue統合PRなど、人間が確認・mergeすべき工程成果物が完成した時点で、Requirement Issueを`人間：PR確認待ち`へ引き渡すこと。
- `人間：PR確認待ち`への引き渡しでは、それ以前のステータスを残さず、ステータス以外のラベルを保持し、更新後の状態を確認できること。
- 対象Pull Requestを人間が確認・mergeした後、次工程へ進める場合は、人間が`AI：作業可能`へ切り替え、別の現在チャット指示を行うこと。
- AIはPull Requestをmergeせず、branchを削除せず、Requirement Issueの完了判断またはcloseを行わないこと。

### RQ-06 Task Planningと中間成果物の継続

- Task Planningで必要な人間判断または計画確認は同じチャットで完結し、回答後に工程別ステータスへの切り替えや同一事項への別承認を要求しないこと。
- 人間確認対象ではないTask PRその他の中間成果物を公開したことだけを理由に、Requirement Issueのステータスを変更しないこと。
- Task PRのreview、merge、Task記録、Issue統合など既存の責務境界は維持し、ステータス簡略化を理由に必要な確認または追跡を省略しないこと。

### RQ-07 状態契約の一元化と整合

- AI開発フロー、Workflow、Reference、Agent指示、関連Skill、テンプレート、説明、および契約テストが、同じ2状態モデル、開始条件、停止条件、引き渡し条件を一貫して扱うこと。
- 状態遷移と工程復元の責務はWorkflowに集約し、個別Skillへ新しい状態機械、工程順序、承認遷移を分散コピーしないこと。
- 関連Skillは自身の能力に必要な入力、出力、責務外を維持し、ステータス変更、次工程の決定、または提出判断を独自に所有しないこと。

### RQ-08 Requirement Issueの初期状態

- Requirement Issue Formは、廃止する工程別ステータスを新規Issueへ初期付与しないこと。
- 新規Issueの初期ラベル方針は、2状態モデルと、`AI：作業可能`および現在のチャット指示を両方必要とする開始条件に整合すること。
- Issueの作成または初期ラベルの付与だけではAI作業を自動実行しないこと。

### RQ-09 既存ラベルとopen Issueの移行

- repository上の工程別ステータスラベルを現行契約から除外し、2状態以外の不要なステータスが通常運用で選択・付与され続けない状態へ移行すること。
- 移行対象となるopen Requirement Issueは、各Issueの永続成果物と現在の作業主体を確認して`AI：作業可能`または`人間：PR確認待ち`へ移行し、旧ステータスや複数ステータスを残さないこと。
- 移行時はステータス以外のラベルを保持し、対象、変更前後、未移行、失敗、および確認結果を追跡できること。
- 過去の要求分析書、設計判断記録、完了済みTask記録など、当時の判断を示す履歴的成果物は新しい状態名へ不要に書き換えないこと。

### RQ-10 品質・承認・安全境界の維持

- 2状態への簡略化後も、変更リスクに応じたself review、独立review、verification、共通品質ゲート、およびPull Requestでの人間確認を維持すること。
- ラベル変更によるAIの自動起動、Pull Requestの自動merge、branchの自動削除、またはRequirement Issueの自動closeを導入しないこと。
- secret、credential、個人情報、または実案件固有情報をラベル、移行記録、成果物、ログへ追加しないこと。

## 受入条件

- AC-01: Requirement Issueの現行ステータス契約で有効なラベルが`AI：作業可能`と`人間：PR確認待ち`の2種類だけであり、ステータスが工程ではなく作業主体として説明されている。
- AC-02: 通常フロー、Agent指示、関連Skill、テンプレート、および検証で、`人間：要求承認待ち`、`人間：タスク承認待ち`、その他の工程固有の承認待ちステータスを使用していない。
- AC-03: 最新Issueのステータスが`AI：作業可能`であり、かつ現在のチャット指示がある場合だけ、AIが対象Requirement Issueの作業を開始できる。
- AC-04: `AI：作業可能`の付与だけではAI作業が起動せず、AIが同ラベルを自己付与して作業権を取得しない。
- AC-05: `人間：PR確認待ち`では、明示的な別作業を除き、人間による対象Pull Requestの確認前にAIがRequirement Issueの次工程を進めない。
- AC-06: ステータス未付与、旧ステータス残存、複数ステータス競合、または永続成果物との矛盾を、AI作業可能または工程完了として扱わず安全停止できる。
- AC-07: 現在工程をIssue、merge済みPull Request、要求分析書、設計判断記録、Task記録、実装、review、verificationから復元でき、ラベルだけを工程完了や承認の証拠にしていない。
- AC-08: 工程途中で必要な人間判断を同じチャットで質問でき、回答済みの同一事項について、別のラベル切り替え、再承認、または新しい開始依頼なしに完成成果物の提出まで継続できる。
- AC-09: チャットで確定した重要な人間判断が該当工程の永続成果物へ必要十分に記録され、後続工程が過去チャットだけに依存しない。
- AC-10: Requirement Analysis PR、設計PR、Issue統合PRなどの人間確認対象が完成した場合だけ、以前のステータスを残さず、非ステータスラベルを保持して`人間：PR確認待ち`へ引き渡せる。
- AC-11: 対象Pull Requestの人間によるmerge後、`AI：作業可能`への切り替えと新しいチャット指示が揃うまで次工程を開始しない。
- AC-12: Task Planningの確認およびTask PRなどの中間成果物で不要なステータス遷移を発生させず、既存のTask review、merge、記録、Issue統合の責務境界を維持している。
- AC-13: Requirement Issue Formが廃止対象ステータスを初期付与せず、採用した初期ラベル方針が2状態モデル、二条件の開始ゲート、およびラベル単独で自動起動しない境界と整合している。
- AC-14: Workflowが状態遷移と工程復元を所有し、個別Skillへ状態機械を分散せず、AI開発フロー、Reference、Agent指示、Skill、テンプレート、説明、契約テストの間に状態契約の矛盾がない。
- AC-15: repository上の不要な工程別ステータスと対象open Requirement Issueについて、移行対象、変更前後、非ステータスラベルの保持、未移行または失敗、移行後の2状態を確認できる。
- AC-16: 過去の要求分析書、設計判断記録、完了済みTask記録などの履歴的成果物が、新しい状態契約へ合わせる目的だけで書き換えられていない。
- AC-17: 既存のreview、verification、共通品質ゲート、人間によるPull Requestのmerge・branch削除・Requirement Issue完了判断が維持され、ラベルを契機とする自動起動・自動merge・自動closeが追加されていない。
- AC-18: 共通品質ゲートと変更リスクに応じた追加検証が成功し、未実施項目、外部移行結果、および残るリスクをIssue統合PRで確認できる。

## 制約

- 対象は、Requirement Issueのステータス契約、AI開発フロー、Workflow、Reference、Agent指示、repository管理下のSkill、Issue Form、テンプレート、契約テスト、repository label、およびopen Issueの移行とする。
- ステータスラベルの責務を作業主体の表示に限定し、工程状態の正本を新たなラベル、本文metadata、中央一覧、外部DB、または別の状態管理機構へ移し替えない。
- Issue #52で確立したWorkflow、Skill、Reference、Agent設定の責務分離と実行時の能力発見を維持する。
- 過去のチャット、要約、ラベル、またはAgent報告だけから工程を推測せず、現在有効な永続成果物を直接確認する。
- Pull Requestのmerge、branch削除、およびRequirement Issueの完了判断は人間だけが行う。
- 人間向けの見出し、説明、判断記録は、技術上の正式名称や機械値を除き自然な日本語で記載する。

## 対象外

- applicationの利用者向け機能、frontend、backend、API、authentication、session、DB、またはデータ契約を変更すること。
- 承認、review、verification、共通品質ゲート、Pull Request、二階層のTask提出など、既存の品質境界そのものを廃止すること。
- ラベル変更だけを契機としてAI作業を自動配信または自動再開する仕組み。
- AIによるPull Requestのmerge、branch削除、Requirement Issueのclose、または人間に代わる最終承認。
- 過去の要求分析書、設計判断記録、完了済みTask記録を新しい状態名へ一括変換すること。
- Requirement Issue Formの具体的な初期付与方式、旧ラベルの削除・保持方式、open Issueの移行手順、変更対象file、Task分解、Agent構成、および具体的な検証コマンドを要求分析で確定すること。

## 重要な人間判断

| 判断対象 | 採用した判断 | 比較・棄却した案 | 根拠 |
|---|---|---|---|
| 現行ステータスの集合 | `AI：作業可能`と`人間：PR確認待ち`の2種類だけを使用する | 要求承認待ち、Task承認待ちなど工程別の状態を維持する | Issueの要求と受入条件で、作業主体だけを示す2状態へ簡略化すると明記されている |
| ステータスの責務 | AIと人間のどちらが次に行動するかだけを示す | ラベルから現在工程、承認済み成果物、Task進捗を復元する | Issueの基本方針で、ラベルは工程ではなく作業主体を表すと明記されている |
| 工程途中の判断 | 同じチャットで質問・回答し、回答後は同一事項を再承認せず作業を継続する | 工程ごとに承認待ちラベルへ切り替え、別の開始依頼を求める | Issueの基本方針と受入条件で、途中判断をチャット内で完結し二重承認をなくすと明記されている |
| 人間への正式な引き渡し | 人間確認対象の完成Pull Requestを提出した時点で`人間：PR確認待ち`へ切り替える | Task計画や中間PRなど工程途中の操作ごとに人間待ちへ切り替える | Issueの基本方針で、人間へボールを返すのはPR完成時だけと明記されている |
| AI作業の開始条件 | `AI：作業可能`と現在のチャット指示の両方を必要とする | ラベル変更だけで自動実行する、またはチャット指示だけで開始する | Issueの開始条件と想定フローで二条件が明記されている |
| 工程の復元方法 | Issue、merge済みPR、要求分析書、設計判断記録、Task記録などの永続成果物を直接確認する | ラベル遷移を工程の正本にする | Issueの基本方針と受入条件で、現在工程を永続成果物から復元すると明記されている |
| 疎結合化との関係 | 状態遷移はWorkflowへ集約し、個別Skillへ状態機械を分散しない | 各Skillへ2状態の遷移規則と工程順序を複製する | IssueがIssue #52の疎結合方針を維持するよう明示している |
| 履歴的成果物 | 当時の判断記録として原則書き換えない | 現行契約に合わせて過去の要求分析書や設計判断記録を一括更新する | Issueの廃止対象と受入条件で、履歴的成果物の不要な書き換えを禁止している |

## 未確定事項

- Requirement Issue Formで`AI：作業可能`を自動付与するか、初期ステータスを付けず人間が明示的に付与するかは、RQ-02とRQ-08を満たすよう後続設計で決定する。
- repository上の旧ステータスラベルを削除するか、通常運用で選択不能な形で履歴用に残すか、およびopen Issueをどの順序・単位で移行するかは、RQ-09とAC-15を満たすよう後続設計で決定する。
- `人間：PR確認待ち`の間に許可する「明示的な別作業」の判定方法と、Pull Request修正依頼を扱う具体的な再開手順は、RQ-02とRQ-05の停止境界を変えない範囲で後続設計へ委ねる。
- 具体的な変更対象file、変更順序、Task分解、Agent構成、移行記録の配置、および検証方法は後続工程で決定する。
- 上記はいずれもIssueで確定済みの2状態、開始条件、引き渡し条件、品質境界を変更しない実現方法の判断であり、要求範囲または受入条件の確定に必要な未回答の人間判断はない。
