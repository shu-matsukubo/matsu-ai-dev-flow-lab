# Issue #68 要求分析

## 元Issue

- [Issue #68: Skill設計方針を独立Skill化し、疎結合ルールを継続的に担保する](https://github.com/shu-matsukubo/matsu-ai-dev-flow-lab/issues/68)

要求原文とIssue登録前の補足は元Issueを参照し、この文書へ重複して正本化しない。

## 目的

Issue #52で実現したSkill間の疎結合を一時点の実装状態にとどめず、今後のSkill追加・変更・レビューで継続して適用できる設計原則として定着させる。Skillを、他Skillや特定工程を知らなくても単独で意味の通る能力として設計できるようにし、密結合や共有知識の重複が再混入した場合に検知できる状態を、既存のWorkflow・Reference・`AGENTS.md`・品質・安全の責務境界を保ったまま実現する。

## 要件

### RQ-01 独立したSkill設計ガイド

- Skillの新規設計、既存Skillの変更、責務の分割・統合・削除判断、およびレビューに利用できる、独立したSkill設計ガイドをrepository管理下のSkillとして提供すること。
- このガイドは業務フローを実行する能力ではなく、Skillそのものの設計妥当性を判断するメタレベルの能力として扱うこと。
- 特定の既存Skill名一覧や固定されたWorkflow構成を前提にせず、Skillの追加・名称変更・削除によってガイド自体の追随変更を必要としないこと。

### RQ-02 Skill間の直接依存の禁止

- 各Skillは、他Skillの名前、パス、内部仕様、または存在を前提にしないこと。
- 別Skillの呼び出し、別Skillの出力取得、または別Skillの成功を、自身の処理手順や成立条件として直接要求しないこと。
- 必要な前提または利用可能な成果は、特定Skillの識別子ではなく、入力として必要な能力契約または成果物の性質で表現すること。

### RQ-03 Workflow制御との分離

- 各Skillは、自身が特定Workflowの何工程目にあるか、または特定の前工程・後工程が存在することを前提にしないこと。
- 各Skillは、前後の能力を呼び出さず、次に実施する能力を決定せず、Workflowの停止・再開・状態遷移を所有しないこと。
- 能力の選択と組み合わせ、実行順序、停止・再開、および遷移はWorkflowが所有し、Skillは一つの能力の提供に限定されること。

### RQ-04 自己完結した能力契約

- 各Skillは、そのSkill単体の定義から、提供能力、適用条件、必要な入力、出力、責務外、および失敗・未実施・不確実な場合の扱いを判断できること。
- 別Skillの説明、内部仕様、または存在を確認しないと能力契約の意味を判断できない構造にしないこと。
- 設計ガイドは、新規Skillと既存Skillの双方について、能力の境界が自己完結しているかを評価できること。

### RQ-05 安定した共通契約との関係

- 正本の定義、repository共通の安全規則、共有判断基準、成果物の共通形式など、複数能力で必要な知識は、別Skillの内部仕様ではなく、安定したrepository contractまたはReferenceとして参照できること。
- 複数Skillで利用する判断基準、規約、または形式を各Skill本文へ競合し得る形で重複コピーせず、共有知識として独立させるべきかを設計ガイドで判断できること。
- Referenceは共有判断知識を所有し、処理実行やWorkflow遷移を所有しないという既存境界を維持すること。

### RQ-06 配置先の責務判定

- Skillの設計・変更時に、対象の記述がSkill固有の能力、Workflowによる工程制御、Referenceによる共有知識、または`AGENTS.md`の安定原則のどこに属するかを判断できること。
- `AGENTS.md`は、Skillを自己完結した単一能力として設計すること、Skill間の直接依存を避けること、工程制御をWorkflowへ、共有判断知識をReferenceへ分離すること、およびSkill追加・変更時に利用可能な設計ガイドを確認することまでを安定原則として保持すること。
- 具体的な禁止例、詳細な判断基準、レビュー観点、および特定Skillに依存する情報を`AGENTS.md`へ複製しないこと。

### RQ-07 現行Skill群との整合

- repository管理下の現行Skill群を新しい設計原則に照らして確認し、Skill間の直接依存、前後工程への依存、Workflow状態遷移の所有、または共有知識の不適切な重複が残っていないかを確認できること。
- 新しい原則への明確な違反が確認された箇所だけを修正し、既存Skillの再度の大規模再編を目的にしないこと。
- 要求分析書、設計判断記録、完了済みTask記録など、当時の判断を保持する履歴的成果物を、新しい設計原則に合わせる目的だけで書き換えないこと。

### RQ-08 継続的な検知

- Skillから別Skill識別名への直接依存、特定の前後工程の要求、SkillによるWorkflow状態遷移の所有、および固定Skill一覧への依存を、契約テストその他の再現可能な検証で継続的に確認できること。
- Skillの追加・名称変更・削除について、無関係なSkillまたは`AGENTS.md`への連鎖修正が不要であることを検証できること。
- 単純な禁止語検索だけに依存して正当な自己宣言、一般語、履歴的記述、または安定した契約参照を違反扱いせず、現在のruntime discoveryと契約テスト方針に整合すること。

### RQ-09 既存品質・安全境界の維持

- Issue #52で導入した`AGENTS.md`、Workflow、Skill、Reference、Agentの責務分離と、実行時に利用可能な能力を発見して選択する方針を維持すること。
- Skill設計ガイドまたは継続検知の導入を理由に、review、verification、submission、承認scope、人間判断、および人間だけが行う最終判断の既存境界を弱めないこと。
- application code、API、authentication、session、DB、または利用者向け機能を変更せず、AI開発フローとその契約検証の範囲で要求を達成すること。

## 受入条件

- AC-01: Skillの新規設計、既存Skillの変更、責務の分割・統合・削除判断、およびレビューに利用できる独立したSkill設計ガイドがrepository管理下に存在する。
- AC-02: Skill設計ガイドが特定の既存Skill名一覧または固定Workflow構成を保持せず、Skillの追加・名称変更・削除だけではガイド自体の変更を必要としない。
- AC-03: repository管理下の各Skillについて、他Skillの名前、パス、内部仕様、または存在を成立条件や処理手順として前提にしていないことを確認できる。
- AC-04: repository管理下の各Skillについて、特定の前工程・後工程を要求せず、次の能力の決定、Workflowの停止・再開、または状態遷移を所有していないことを確認できる。
- AC-05: 各Skillの単体定義から、提供能力、適用条件、入力、出力、責務外、および失敗・未実施・不確実な場合の扱いを判断できる。
- AC-06: Skill固有処理、Workflowによる能力の構成・順序・遷移、Referenceによる共有判断知識、および`AGENTS.md`の安定原則の責務境界が設計ガイドで判断可能になっている。
- AC-07: 複数Skillで利用する判断基準、規約、または共通形式について明確な正本を特定でき、各Skillへ競合し得る形で重複保持されていない。
- AC-08: `AGENTS.md`がSkill設計の安定原則と設計ガイド確認の入口だけを保持し、具体的な禁止例、詳細手順、固定Skill一覧、またはSkill固有のレビュー観点を複製していない。
- AC-09: 現行Skill群の全対象について新しい設計原則との整合確認結果を追跡でき、明確な違反だけが修正され、違反のないSkillや履歴的成果物が不要に変更されていない。
- AC-10: Skill間の直接依存、前後工程依存、Workflow状態遷移の所有、および設計ガイドの固定Skill一覧依存を、契約テストその他の再現可能な検証で検知できる。
- AC-11: 継続検知が単純な禁止語検索だけに依存せず、許可される自己宣言、一般的な能力契約、Referenceまたは安定したrepository contractへの参照を誤って違反扱いしないことを、肯定経路と否定経路で確認できる。
- AC-12: 代表的なSkillの追加・名称変更・削除を模擬または再現可能な方法で確認し、無関係なSkillおよび`AGENTS.md`へ連鎖修正が不要であることを示せる。
- AC-13: Issue #52で確立した実行時の能力発見と、`AGENTS.md`、Workflow、Skill、Reference、Agentの責務分離が維持されている。
- AC-14: 既存のreview、verification、submission、承認scope、人間判断、Pull Requestのmerge、branch削除、およびRequirement Issueの完了判断に関する品質・安全境界が維持されている。
- AC-15: application code、API、authentication、session、DB、および利用者向け機能に変更がなく、共通品質ゲートと変更リスクに応じた追加検証が成功し、未実施項目と残るリスクをIssue統合PRで確認できる。

## 制約

- 対象は、repository管理下の`.agents/skills/`、Skill設計方針を提供する新しいメタSkill、`AGENTS.md`の安定原則、AI開発フローのoverview・Workflow・Reference、Skill関連の契約テスト、およびSkillの作成・変更・レビュー時の利用方法とする。
- Skill設計ガイドを厳格な固定テンプレートとして扱わず、他Skillを知らなくても単独能力として成立するという不変条件と責務境界の判断を中心にする。
- Skillを完全に孤立させることを目的とせず、Referenceまたは安定したrepository contractへの必要な参照を許容し、変化しやすいSkill同士を直接結合しないことを重視する。
- 具体的なメタSkillの名称、配置、能力契約、利用方法、整合確認の記録形式、および継続検知の実装方式は、この要求と受入条件を満たすよう後続設計で決定する。
- Issue #52で確立した現在のAI開発フロー、品質、承認、および安全の境界を弱めない。
- Pull Requestのmerge、branch削除、およびRequirement Issueの完了判断は人間だけが行う。
- 人間向けの見出し、説明、判断記録は、技術上の正式名称や機械値を除き自然な日本語で記載する。
- secret、credential、個人情報、または実案件固有情報を成果物や検証ログへ記録しない。

## 対象外

- application code、frontend、backend、API、authentication、session、DB、データ契約、または利用者向け機能を変更すること。
- repository管理外のCodex標準Skill、plugin、外部サービス、または外部Skill定義を変更すること。
- 現行Skill群を新しい構成へ大規模に再編すること自体を目的にすること。
- 要求分析書、設計判断記録、完了済みTask記録などの履歴的成果物を、新しい原則に合わせて一括更新すること。
- SkillからReferenceやrepository共通の安定した契約への参照を一律に禁止し、必要な共有知識を各Skillへ複製すること。
- 設計ガイドを固定書式への適合だけで判定するものにすること、または単純な禁止語検索だけで疎結合を判定すること。
- 要求分析工程で、最終的なメタSkill名、file配置、既存Skillの修正対象、検査構造、テスト実装、Task分割、またはAgent構成を確定すること。
- AIによるPull Requestのmerge、branch削除、Requirement Issueのclose、または人間に代わる最終承認を導入すること。
